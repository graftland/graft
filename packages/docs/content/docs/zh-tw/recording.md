---
title: 記錄
description: 要求變更在執行、提交及成功之前，先取得已確認的記錄。
---

**記錄者**是執行單元中持有部署記錄角色的外掛。變更涉及記錄範圍內的實例時，核心在每個階段向記錄者傳送一筆記錄，並等待其確認。

- 意圖記錄確認之前，不執行任何生命週期操作。
- 提交決定確認之前，不啟用任何路由。
- 結論記錄確認之後，才回報 `Accepted`。
- 停止、終止及結束觀察從不等待記錄者。

## 宣告角色

記錄是部署資料。閉包中包含 `scope` 內實例的每個變更都須記錄，請求不能選擇略過。

```ts
import { Layer } from "effect"

import { Kernel } from "@graftland/graft"
import { Units } from "@graftland/plugin-remote"

declare const instances: Kernel.Deployment["instances"]

export const kernel = Kernel.layer({
	authority: "shop",
	maxUnits: 8,
	instances,
	recording: { recorder: "release", instance: "release", scope: ["checkout"] },
}).pipe(Layer.provide(Units.layer))
```

| 欄位         | 意義                                                      |
| ------------ | --------------------------------------------------------- |
| `recorder`   | 外掛註冊時使用的角色名稱。                                |
| `instance`   | 唯一可持有該角色的實例，角色由其所在的單元持有。          |
| `scope`      | 需要記錄的變更所涉及的實例。                              |
| `maxRecords` | 未確認與已預留記錄的上限，超出的新工作會被拒絕。預設 64。 |

## 從設定檔啟動

在設定檔中宣告記錄者，再執行 `graft start --watch`：

```yaml title="graft.yml"
- id: release
  name: "@graftland/plugin-release/Recorder"
  recording: { role: release }
  config:
    recorder: release
    directory: ./.graft/journal

- id: checkout
  name: ./plugins/checkout.mjs
```

| 設定              | 規則                                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `recording.role`  | 此項目持有的角色，須與外掛註冊的角色一致。任何實作記錄協定的外掛都可以持有。                                                 |
| `recording.scope` | 需要記錄變更的項目 id。省略時包含其他所有應用項目，包括巢狀和停用的項目；空清單表示不記錄。                                  |
| 角色持有者        | 僅一個啟用的應用項目可以宣告角色，不能用於群組。記錄者先獨立啟動，再啟動需要記錄的項目。                                     |
| 後續編輯          | 相同宣告可重複提交。變更或移除角色、持有者或範圍須重新啟動應用；監看模式回報 `RecordingConflict`。增刪項目也會改變預設範圍。 |

## 執行記錄者

`@graftland/plugin-release/Recorder` 是一般的記錄者。將它部署為
`instance`，輸入為
`{ recorder: "release", directory: "./journal" }`：它把每筆記錄附加到該目錄的日誌，同步到磁碟後才確認。不設
`directory` 時，記錄只存於所在單元的記憶體。第三方外掛透過同一個
`Recording.Recorder` 服務持有該角色，第一方沒有特殊通道。

```ts
import { Effect, Stream } from "effect"

import { Plugin } from "@graftland/graft"
import { Recording } from "@graftland/plugin-remote"

export default Plugin.make({
	name: "audit-recorder",
	inject: [Recording.Recorder],
	apply: Effect.fn(function* () {
		const recorder = yield* Recording.Recorder
		yield* recorder.records.pipe(
			Stream.runForEach((record) => recorder.acknowledge(record)),
			Effect.forkScoped,
		)
		yield* recorder.register("release")
	}),
})
```

| 規則     | 行為                                                                      |
| -------- | ------------------------------------------------------------------------- |
| 身分     | 單元的控制通道標明化身，外掛不能代替其他化身註冊或確認。                  |
| 註冊     | 接受來自承載 `instance` 之單元的註冊；該單元成為目前單元後授權才生效。    |
| 確認     | 儲存之後再確認。重複確認會被忽略；內容、擁有者或化身不符則被拒絕。        |
| 重新連線 | 同一化身再次註冊時，核心重送其尚未確認的記錄。                            |
| 持久性   | 設定 `directory` 時寫入磁碟上的日誌，否則沒有。核心保留記錄直到它被確認。 |

## 讀取日誌

日誌由分段組成，每筆記錄一行；並行的變更交錯寫入。`@graftland/plugin-release` 的
`Journal.history(directory)`
不需執行中的核心即可讀取，依核心執行與變更 id 各回傳一份摘要：階段、成員、目標、結局、`concluded`，以及最新一筆記錄中每個成員的期望與實際目標、健康狀態、本次嘗試的情況（`NotStarted`、`Started`、`Ready`、`Failed`、`Stopped`）、階段及診斷參照。診斷仍在保留期內時，摘要也包含呈現後的 cause（至多 4096 個字元）。

| 情形               | 結果                                                                           |
| ------------------ | ------------------------------------------------------------------------------ |
| 同一筆記錄再次送達 | 不寫第二行即確認。同一 id 但內容不同則被拒絕。                                 |
| 寫入或同步失敗     | 不確認；下一次附加先截掉殘留的半行，單元執行期間每秒重試，因此該變更維持受阻。 |
| 行程在寫入中途停止 | 記錄者開啟日誌時移除被截斷的最後一行；較早的損壞行會使日誌拒絕開啟。           |
| 行程在變更中途停止 | 該變更只有意圖而沒有結論：`concluded` 為 `false`；成員事實顯示已經執行了什麼。 |
| 核心重新啟動       | 變更 id 從 `change-1` 重新開始；執行 id 把兩次執行區分開。                     |
| 舊版內嵌診斷       | 不自動遷移舊日誌檔案。此格式應使用新目錄。                                     |

## 核心重新啟動後復原

設定 `directory`
時，記錄者在向新核心註冊前讀取日誌。日誌行保留每個請求的鍵及正規化請求文字。

| 已記錄的狀態                 | 重新啟動後                                                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 帶鍵的意圖，無論是否已有結論 | 相同鍵及正規化請求以 `AlreadyRecorded` 拒絕；`conflicts` 指出先前的 `"<run>/<change>"`。相同鍵下的不同請求以 `KeyConflict` 拒絕，不再次執行工作。 |
| 有意圖但沒有結論             | 核心依原執行及變更 id 補記結論。歷史顯示 `concluded: true`、沒有結局、階段為 `Interrupted`，並附上成員目前的事實。未知的目標仍然未知。            |
| 已壓縮分段中的記錄           | 復原時保留其請求鍵及未完成變更的資訊。                                                                                                            |
| 記憶體記錄者                 | 核心重新啟動後，請求鍵及記錄不保留。                                                                                                              |

`Interrupted`
結論不宣稱先前工作成功或失敗，也不繼續或撤銷先前動作。診斷過期不會移除請求鍵或持久的成員事實。

## 保留診斷

**診斷參照**是不透明的識別碼，指向 `directory/diagnostics`
中呈現後的 cause；較長的 cause 核心只傳送前 4096 個字元，完整的 cause 在核心執行期間可依 Change
id 查詢。日誌行只儲存參照及到期時間，不包含 cause。診斷檔案可能含有秘密，應像其他敏感應用資料一樣限制該目錄的存取權限。

| 設定或欄位            | 行為                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------- |
| `diagnosticRetention` | 記錄者輸入，例如 `"7 days"`；必須是有限的非負時長。預設 `"30 days"`。                        |
| 保留期起點            | 首次儲存診斷時。修改設定只影響新診斷。                                                       |
| `diagnosticReference` | 歷史摘要中的參照及到期時間；沒有 cause 時為 `None`。                                         |
| `diagnosticStatus`    | `None`、`Available` 或 `Expired`。過期摘要顯示 `Diagnostic expired`；結局及參照仍然保留。    |
| 過期檔案              | 記錄者開啟日誌、附加之前及每小時維護時移除。記錄者停止時，歷史讀取會回報過期，但不移除檔案。 |
| 寫入或同步失敗        | 診斷及日誌項目都儲存並同步之後才確認記錄。                                                   |

## 壓縮分段

記錄者在啟動及每小時維護時壓縮符合條件的分段。透過 `Journal.open`
開啟的日誌也提供 `compact` 及 `prune` effect，供顯式維護。

| 規則     | 行為                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------ |
| 條件     | 連續的已關閉分段，其中每個變更都有結論記錄時，可以合併。含有未完成變更的分段及目前開啟的分段維持原狀。 |
| 歷史     | 壓縮保留每筆記錄、順序、診斷參照及 `Journal.history` 結果。減少的是分段檔案，不是保留的結局記錄。      |
| 壓縮中斷 | 重新開啟時讀取完整的舊分段或替換分段集合，不重複記錄。後續維護會移除被取代的檔案。                     |
| 所有權   | 一個目錄由一個記錄者持有。顯式維護應透過其日誌控制代碼執行，不要為同一目錄開啟另一個寫入者。           |

## 缺少記錄時

| 情形                       | 結果                                                                  |
| -------------------------- | --------------------------------------------------------------------- |
| 提交時沒有存活的記錄者     | 在配置變更 id 之前以 `RecordingUnavailable` 拒絕。                    |
| 未確認的記錄過多           | 以 `RecordingCapacity` 拒絕，不會淘汰任何記錄義務。                   |
| 記錄者不再確認或已結束     | 後續工作等待；預算照常耗盡，依一般的[結局規則](../transitions/)收尾。 |
| 只缺結論記錄               | 執行已經完成並維持原狀。不回報結局；取消也不改變任何事物。            |
| 記錄者帶著未確認的義務結束 | 新的化身不能確認這些義務，`status.recording.blocked` 維持為 `true`。  |
| 變更會替換記錄者所在的單元 | 若該變更需要記錄，或存在未確認的義務，以 `SelfReplacement` 拒絕。     |

`status.recording` 顯示目前關卡、未確認的記錄及其是否受阻。`kernel.recording` 與
[`client.recording`](../control/)
列出所有未確認的記錄，包括已結束記錄者的記錄。核心行程遺失時，未確認記錄的傳送佇列隨之遺失；持久日誌仍可用於復原。
