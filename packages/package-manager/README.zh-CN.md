# @graftland/package-manager

[English](https://github.com/graftland/graft/blob/main/packages/package-manager/README.md)
| 简体中文 |
[繁體中文](https://github.com/graftland/graft/blob/main/packages/package-manager/README.zh-TW.md)

使用 npm、pnpm 或 Yarn 安装依赖，并在失败时回滚。

支持的最低 Node.js 版本是 22.19。Windows 按现状提供。Windows 上的进程树清理和回滚没有经过验证，也不作承诺。

```sh
npm install @graftland/package-manager effect
```

`make` 会检测项目所用的包管理器。它的 `install`
可以添加、更新或移除依赖。如果安装失败，它会恢复 `package.json`
和锁文件。`graft add` 和 `graft remove` 使用它。

## 安装的所有权与恢复

每个项目只使用一个管理器。调用方必须让管理器及其子进程独占项目的写入权限。这从一次
`install` 调用开始，持续到它结束，包括恢复阶段。

- 在此期间，不要编辑项目文件。
- 不要同时运行另一个安装程序。
- 同一个管理器内的调用是串行的。Graft 不会在多个管理器、编辑器或进程之间强制加锁。

在 POSIX 上，进程清理只覆盖安装程序最初的进程组。安装脚本和恢复脚本不得创建不受管理的写入者。例如，处于独立进程组的子进程，以及持续写入项目文件的守护进程。Graft 不提供操作系统级别的隔离，也不会发现逃逸的写入者。确认最初的进程组已经停止，并不能证明所有可能的后代都已经停止。违反这条规则的脚本不在回滚保证的范围内。

受管理的路径必须是普通文件，或者不存在。`make` 和每次 `install` 都使用 `lstat`
检查快照集合。快照集合包括
`package.json`、锁文件，以及被跟踪的配置文件和安装状态文件。

- 符号链接会被拒绝，包括悬空链接。其他文件类型也会被拒绝。
- 错误是
  `UnsupportedFileTypeError`。它在任何事务写入之前、任何安装程序启动之前抛出。
- 错误会给出 `path` 和 `fileType`。链接及其目标保持不变。
- 在事务开始之前的拒绝，不需要恢复，也不会让管理器不可用。

### 回滚

当安装在提交之前失败或被中断时，会执行回滚。回滚需要先确认最初的进程组已经停止。然后它会做这些事：

- 把已备份的包文件逐字节恢复，并保留它们记录下来的权限位和所有者。
- 移除安装之前不存在的被跟踪文件。

被跟踪的文件包括
`package.json`、锁文件，以及管理器所跟踪的包管理器配置文件和安装状态文件。

回滚会覆盖安装期间所做的更改。它不会检测冲突，也不会合并编辑。

如果项目已经有所选包管理器的锁文件，恢复阶段还会尝试修复
`node_modules`。恢复错误会与原始失败一起保留。不承诺在进程崩溃之后恢复。

### 文件写入与进程清理

已接受的文件写入有一个完成边界。取消会等待原生操作完成，然后才进行回滚、清理快照，以及释放管理器的锁。事务会跟踪它自己的文件写入以及最初的安装程序进程组。创建快照和回滚写入也有同样的完成保证。

每个安装进程和每个恢复进程都有十分钟的退出等待时间。取消或超时会在恢复文件之前关闭它的进程 scope。

- 进程会收到 SIGTERM。
- 如果五秒后它还没有停止，就会收到 SIGKILL。
- 在 POSIX 上，即使 kill 成功，也必须确认原进程组已不存在。每 20 毫秒检查一次，最多追加 100 次检查（等待两秒），给短暂残留的僵尸进程组留出回收窗口。EPERM 视为仍然存在，不视为已消失。
- 如果进程组仍存在或检查失败，则终止未获确认：管理器保留快照，不执行回滚和恢复安装，并进入
  `RecoveryRequired`。
- 进程清理失败会与安装和恢复的失败一起保留在返回的 cause 中。
- 退出超时不包括进程清理和文件恢复，也不是整个“安装并恢复”操作的截止时间。

Node 适配器可能会把原始的操作系统 errno 替换为通用的 kill 失败。只有 POSIX 检查确认进程组不存在后，PackageManager 才消解携带 ESRCH 的信号失败，或适配器特定的
`Unknown` kill 错误（cause 为
`Failed to kill child process`）。同一 Cause 中的其他原因仍然保留，包括 join 失败、其他 kill 错误、defect 和中断。进程组仍存在时保留原始 Cause；检查失败时保留两个完整 Cause。

## 已提交的安装与快照清理

`install` 成功的结果表示依赖更改已经提交。

`result.snapshotCleanupFailure` 是 `Option<SnapshotCleanupFailure>`：

- `None` 表示快照删除成功。
- `Some` 包含 `snapshotDirectory` 和完整的清理 `cause`，包括 defect。

提交之后删除快照失败，不会让这次安装变成失败，也不会触发回滚。管理器仍然可用，`recoveryRequired`
仍然是 `None`。

调用方应该这样做：

- 检查这个字段，报告或记录它的 Cause。
- 在文件系统问题解决之后，重试删除该快照目录。该目录可能已被部分删除。
- 不要恢复旧的快照，也不要仅仅因为快照删除失败就重复安装。那些更改已经提交了。
- 保留下来的数据可能包含凭据，所以要确保它最终被删除。

提交之前的失败仍然会使操作失败并执行回滚。任何快照清理失败都会与原始失败合并。

取消可能会使提交之后的结果无法送达。这并不能证明更改已被撤销。这种情况下，清理失败会保留在被中断的 Cause 中。

## 何时需要手动恢复

在安装更改项目文件之前，会先保存一份快照。快照位于操作系统临时目录中一个私有的
`graft-recovery-*` 目录里。

- 只有成功的安装或完整的回滚，才允许删除快照并运行下一次安装。
- 已提交但快照删除失败的安装，按上文所述报告。
- 进程终止和事务完成是两个独立的条件。停止写入者，回滚才能开始，但这并不证明回滚成功。

只要有任何一个回滚步骤失败，管理器就会保留快照，并需要手动恢复。这包括在恢复之前或之后恢复文件，以及运行恢复安装程序。即使最后的文件恢复成功，这条规则也适用，因为失败的恢复可能让
`node_modules` 不完整。

管理器如何恢复一个文件：

1. 在目标目录中以独占方式创建临时文件，模式为 `0600`。
2. 当平台报告了保存的 uid/gid 时，先恢复它们，然后恢复权限位。
3. 对文件执行 sync 并关闭。
4. 把该文件重命名覆盖到目标上。

元数据失败和临时文件清理失败同样需要手动恢复，并保留在 Cause 中。时间戳、ACL 和扩展属性不会被记录。

如果无法确认进程已经终止，就不会再进行任何恢复。这是为了避免与可能仍在写入的进程发生冲突。

### 恢复错误

失败调用的 Cause 会保留原始失败以及所有回滚和终止的失败。它包含一个
`RecoveryRequiredError`，其字段如下：

- `snapshotDirectory` 给出保存的位置。
- `directory` 标识项目。
- `recoveryCause` 保留完整的原始 Cause 和恢复 Cause。
- `operation`：在写入者已停止但回滚不完整时是 `rollback`；在无法确认终止时是
  `install` 或 `recover`，此时 `processId` 和 `terminationCause`
  给出进程的详细信息。

取消之后，调用方还可以读取 `manager.recoveryRequired`。它是一个产出
`Option<RecoveryRequiredError>` 的 Effect。调用方不需要去捕获被中断的调用。

管理器会永久拒绝之后所有的 `install`
调用，并返回这个带类型的错误。这包括已经排队的调用，以及变更集为空的调用。`readState`
仍然是只读的诊断操作。在项目文件不完整时，它可能失败。

### 手动恢复的步骤

1. 找出失败的安装程序及其所有后代，并停止它们。记录下来的进程 ID 只用于诊断，不能证明之后具有相同 ID 的进程属于这次安装。在所有写入者停止之前，不要恢复文件，也不要启动另一个安装程序。
2. 解决阻止恢复的文件系统问题，例如文件权限。然后恢复文件：
   - 打开 `snapshotDirectory` 中的 `snapshot.json`。检查其中的项目 `directory`
     和 `agent`。
   - 对每个 `files` 条目，把指定的 `backup` 中的字节复制到项目 `name`
     旁边的临时文件中。以私有、独占的方式创建该临时文件。
   - 当 `uid` 和 `gid` 不为 null 时，恢复记录下来的值，然后恢复
     `mode`。请在替换目标之前完成这些。
   - 这些元数据值是 JSON 整数。`mode`
     是数值形式的权限位掩码，不是八进制格式的字符串。
   - 按需创建父目录。
   - `backup` 为 null 表示该文件原本不存在。如果它现在存在，就删除它。
3. 使用所选的包管理器，基于已恢复的清单文件和锁文件修复
   `node_modules`。该进程停止之后，如果它重写了快照中的文件，请再次恢复这些文件。快照不包含
   `node_modules`。
4. 验证项目。然后删除快照，并用 `make`
   创建一个新的管理器。旧的管理器没有重置操作。

快照可能包含来自包管理器配置文件的凭据。请保持私有。它们在管理器和 Effect
scope 关闭之后依然存在。但是操作系统可能会清理临时目录。如果手动恢复会被推迟，请把保留的快照复制到一个安全的私有位置。

这个机制不是崩溃恢复，也不是跨进程的项目锁。创建新的管理器，并不会让仍在运行的安装程序变得安全。

## 包管理器声明

共享的 `PackageManagerDeclaration` Schema 接受 `npm`、`pnpm` 或
`yarn`，后跟精确的 SemVer 版本（版本部分最多 256 个字符），可包含预发布标识。它拒绝空后缀、版本及预发布数字标识的前导零、版本范围、标签、URL 和首尾空白。

`+` 后缀仅用于
[Corepack hash](https://github.com/nodejs/corepack#when-authoring-packages)：支持
`sha224`、`sha256`、`sha384`、`sha512`，后跟点号及分别为 56、64、96、128 个字符的小写十六进制摘要。不支持普通 SemVer
build metadata。这里只校验声明语法，不下载或验证包管理器压缩包的真实性。

创建项目与检测包管理器使用同一个 Schema，可从
`@graftland/package-manager/PackageManagerDeclaration`
导入。创建时逐字保留传入的声明；检测时显式指定的 `agent`
仍优先于 manifest 声明。
