# @graftland/package-manager

[English](https://github.com/graftland/graft/blob/main/packages/package-manager/README.md)

[简体中文](https://github.com/graftland/graft/blob/main/packages/package-manager/README.zh-CN.md)

使用 npm、pnpm 或 Yarn 安裝相依套件，並在失敗時還原。

支援的最低 Node.js 版本是 22.19。Windows 依現況提供。Windows 上的行程樹清理和還原沒有經過驗證，也不作承諾。

```sh
npm install @graftland/package-manager effect
```

`make` 會偵測專案所用的套件管理器。它的 `install`
可以新增、更新或移除相依套件。如果安裝失敗，它會還原 `package.json`
和鎖定檔。`graft add` 和 `graft remove` 使用它。

## 安裝的所有權與復原

每個專案只使用一個管理器。呼叫端必須讓管理器及其子行程獨占專案的寫入權限。這從一次
`install` 呼叫開始，持續到它結束，包括復原階段。

- 在此期間，不要編輯專案檔案。
- 不要同時執行另一個安裝程式。
- 同一個管理器內的呼叫是循序的。Graft 不會在多個管理器、編輯器或行程之間強制加鎖。

在 POSIX 上，行程清理只涵蓋安裝程式最初的行程群組。安裝腳本和復原腳本不得建立不受管理的寫入者。例如，處於獨立行程群組的子行程，以及持續寫入專案檔案的常駐程式。Graft 不提供作業系統層級的隔離，也不會發現逃逸的寫入者。確認最初的行程群組已經停止，並不能證明所有可能的後代都已經停止。違反這條規則的腳本不在還原保證的範圍內。

受管理的路徑必須是一般檔案，或者不存在。`make` 和每次 `install` 都使用 `lstat`
檢查快照集合。快照集合包括
`package.json`、鎖定檔，以及被追蹤的設定檔和安裝狀態檔。

- 符號連結會被拒絕，包括懸空連結。其他檔案類型也會被拒絕。
- 錯誤是
  `UnsupportedFileTypeError`。它在任何交易寫入之前、任何安裝程式啟動之前擲出。
- 錯誤會給出 `path` 和 `fileType`。連結及其目標保持不變。
- 在交易開始之前的拒絕，不需要復原，也不會讓管理器無法使用。

### 還原

當安裝在提交之前失敗或被中斷時，會執行還原。還原需要先確認最初的行程群組已經停止。然後它會做這些事：

- 把已備份的套件檔案逐位元組還原，並保留它們記錄下來的權限位元和擁有者。
- 移除安裝之前不存在的被追蹤檔案。

被追蹤的檔案包括
`package.json`、鎖定檔，以及管理器所追蹤的套件管理器設定檔和安裝狀態檔。

還原會覆蓋安裝期間所做的變更。它不會偵測衝突，也不會合併編輯。

如果專案已經有所選套件管理器的鎖定檔，復原階段還會嘗試修復
`node_modules`。復原錯誤會與原始失敗一起保留。不承諾在行程當機之後復原。

### 檔案寫入與行程清理

已接受的檔案寫入有一個完成邊界。取消會等待原生操作完成，然後才進行還原、清理快照，以及釋放管理器的鎖。交易會追蹤它自己的檔案寫入以及最初的安裝程式行程群組。建立快照和還原寫入也有同樣的完成保證。

每個安裝行程和每個復原行程都有十分鐘的結束等待時間。取消或逾時會在還原檔案之前關閉它的行程 scope。

- 行程會收到 SIGTERM。
- 如果五秒後它還沒有停止，就會收到 SIGKILL。
- 在 POSIX 上，即使 kill 成功，也必須確認原行程群組已不存在。每 20 毫秒檢查一次，最多追加 100 次檢查（等待兩秒），給短暫殘留的殭屍行程群組留出回收時間。EPERM 視為仍然存在，不視為已消失。
- 如果行程群組仍存在或檢查失敗，則終止未獲確認：管理器保留快照，不執行回復和復原安裝，並進入
  `RecoveryRequired`。
- 行程清理失敗會與安裝和復原的失敗一起保留在回傳的 cause 中。
- 結束逾時不包括行程清理和檔案還原，也不是整個「安裝並復原」操作的截止時間。

Node 轉接器可能會把原始的作業系統 errno 取代為通用的 kill 失敗。只有 POSIX 檢查確認行程群組不存在後，PackageManager 才消解帶有 ESRCH 的訊號失敗，或轉接器特定的
`Unknown` kill 錯誤（cause 為
`Failed to kill child process`）。同一 Cause 中的其他原因仍然保留，包括 join 失敗、其他 kill 錯誤、defect 和中斷。行程群組仍存在時保留原始 Cause；檢查失敗時保留兩個完整 Cause。

## 已提交的安裝與快照清理

`install` 成功的結果表示相依套件的變更已經提交。

`result.snapshotCleanupFailure` 是 `Option<SnapshotCleanupFailure>`：

- `None` 表示快照刪除成功。
- `Some` 包含 `snapshotDirectory` 和完整的清理 `cause`，包括 defect。

提交之後刪除快照失敗，不會讓這次安裝變成失敗，也不會觸發還原。管理器仍然可用，`recoveryRequired`
仍然是 `None`。

呼叫端應該這樣做：

- 檢查這個欄位，回報或記錄它的 Cause。
- 在檔案系統問題解決之後，重試刪除該快照目錄。該目錄可能已被部分刪除。
- 不要還原舊的快照，也不要僅僅因為快照刪除失敗就重複安裝。那些變更已經提交了。
- 保留下來的資料可能包含憑證，所以要確保它最終被刪除。

提交之前的失敗仍然會使操作失敗並執行還原。任何快照清理失敗都會與原始失敗合併。

取消可能會使提交之後的結果無法送達。這並不能證明變更已被撤銷。這種情況下，清理失敗會保留在被中斷的 Cause 中。

## 何時需要手動復原

在安裝變更專案檔案之前，會先儲存一份快照。快照位於作業系統暫存目錄中一個私有的
`graft-recovery-*` 目錄裡。

- 只有成功的安裝或完整的還原，才允許刪除快照並執行下一次安裝。
- 已提交但快照刪除失敗的安裝，依上文所述回報。
- 行程終止和交易完成是兩個獨立的條件。停止寫入者，還原才能開始，但這並不證明還原成功。

只要有任何一個還原步驟失敗，管理器就會保留快照，並需要手動復原。這包括在復原之前或之後還原檔案，以及執行復原安裝程式。即使最後的檔案還原成功，這條規則也適用，因為失敗的復原可能讓
`node_modules` 不完整。

管理器如何還原一個檔案：

1. 在目標目錄中以獨占方式建立暫存檔，模式為 `0600`。
2. 當平台回報了儲存的 uid/gid 時，先還原它們，然後還原權限位元。
3. 對檔案執行 sync 並關閉。
4. 把該檔案重新命名覆蓋到目標上。

中繼資料失敗和暫存檔清理失敗同樣需要手動復原，並保留在 Cause 中。時間戳記、ACL 和擴充屬性不會被記錄。

如果無法確認行程已經終止，就不會再進行任何還原或復原。這是為了避免與可能仍在寫入的行程發生衝突。

### 復原錯誤

失敗呼叫的 Cause 會保留原始失敗以及所有還原和終止的失敗。它包含一個
`RecoveryRequiredError`，其欄位如下：

- `snapshotDirectory` 給出儲存的位置。
- `directory` 識別專案。
- `recoveryCause` 保留完整的原始 Cause 和復原 Cause。
- `operation`：在寫入者已停止但還原不完整時是 `rollback`；在無法確認終止時是
  `install` 或 `recover`，此時 `processId` 和 `terminationCause`
  給出行程的詳細資訊。

取消之後，呼叫端還可以讀取 `manager.recoveryRequired`。它是一個產出
`Option<RecoveryRequiredError>` 的 Effect。呼叫端不需要去攔截被中斷的呼叫。

管理器會永久拒絕之後所有的 `install`
呼叫，並回傳這個帶型別的錯誤。這包括已經排隊的呼叫，以及變更集為空的呼叫。`readState`
仍然是唯讀的診斷操作。在專案檔案不完整時，它可能失敗。

### 手動復原的步驟

1. 找出失敗的安裝程式及其所有後代，並停止它們。記錄下來的行程 ID 只用於診斷，不能證明之後具有相同 ID 的行程屬於這次安裝。在所有寫入者停止之前，不要還原檔案，也不要啟動另一個安裝程式。
2. 解決阻止還原的檔案系統問題，例如檔案權限。然後還原檔案：
   - 開啟 `snapshotDirectory` 中的 `snapshot.json`。檢查其中的專案 `directory`
     和 `agent`。
   - 對每個 `files` 項目，把指定的 `backup` 中的位元組複製到專案 `name`
     旁邊的暫存檔中。以私有、獨占的方式建立該暫存檔。
   - 當 `uid` 和 `gid` 不為 null 時，還原記錄下來的值，然後還原
     `mode`。請在取代目標之前完成這些。
   - 這些中繼資料值是 JSON 整數。`mode`
     是數值形式的權限位元遮罩，不是八進位格式的字串。
   - 視需要建立父目錄。
   - `backup` 為 null 表示該檔案原本不存在。如果它現在存在，就刪除它。
3. 使用所選的套件管理器，基於已還原的清單檔和鎖定檔修復
   `node_modules`。該行程停止之後，如果它重寫了快照中的檔案，請再次還原這些檔案。快照不包含
   `node_modules`。
4. 驗證專案。然後刪除快照，並用 `make`
   建立一個新的管理器。舊的管理器沒有重設操作。

快照可能包含來自套件管理器設定檔的憑證。請保持私有。它們在管理器和 Effect
scope 關閉之後依然存在。但是作業系統可能會清理暫存目錄。如果手動復原會被延後，請把保留的快照複製到一個安全的私有位置。

這個機制不是當機復原，也不是跨行程的專案鎖。建立新的管理器，並不會讓仍在執行的安裝程式變得安全。

## 套件管理器宣告

共用的 `PackageManagerDeclaration` Schema 接受 `npm`、`pnpm` 或
`yarn`，後接精確的 SemVer 版本（版本部分最多 256 個字元），可包含預發布識別碼。它拒絕空後綴、版本及預發布數字識別碼的前置零、版本範圍、標籤、URL 和首尾空白。

`+` 後綴僅用於
[Corepack hash](https://github.com/nodejs/corepack#when-authoring-packages)：支援
`sha224`、`sha256`、`sha384`、`sha512`，後接點號及分別為 56、64、96、128 個字元的小寫十六進位摘要。不支援一般 SemVer
build metadata。這裡只檢查宣告語法，不下載或驗證套件管理器壓縮檔的真實性。

建立專案與偵測套件管理器使用同一個 Schema，可從
`@graftland/package-manager/PackageManagerDeclaration`
匯入。建立時完整保留傳入的宣告；偵測時明確指定的 `agent`
仍優先於 manifest 宣告。
