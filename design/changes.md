## 0. 摘要

今天改变一个运行中的插件有两族、十条路径。它们的身份、顺序、所有权、取消语义、失败处理和结局各不相同；为了不互相破坏，还有一整套保护机制。本文提议：

> **一切变更都经过同一个转换协议。**
> 一次变更有稳定的身份和所有者，按显式的成员规则选出受影响的 fork；每个 fork 按请求意图和适用条件选择策略（就地、重启、重叠，将来加交接）；所有变更用同一套准入、取消、观察和结局。

要说清楚的边界：

- **统一的是协议，不是恢复语义。**
  恢复不是原子事务：就地更新和试运行期间产生的外部效果撤销不了。批次结局必须带上每个成员的结局和残留状态，而不是一个总的
  `Recovered`。
- **开发与生产共用一条流水线。**
  HMR 不再是独立路径，而是发布流水线的开发配置（2.10）。
- **统一不等于删掉不变量。**
  每删一个保护机制，都要指出替代机制在哪个线性化点保证同一性质（第 4 节）。

### 1.2 `replace` 的判定规则

`replace`
的语义比「一个失败、整批回滚」精细得多（`replacement.ts:177-230`、`:323-438`，测试见
`replacement-races.test.ts`）：

| 情况                                                      | 被改变   | 决定结果 | 被恢复   |
| --------------------------------------------------------- | -------- | -------- | -------- |
| 运行源插件的 fork                                         | 是       | 是       | 是       |
| 替换前已经失败的 fork                                     | 是       | 否       | 是       |
| 原本就运行目标插件的 fork                                 | 否       | 否       | 否       |
| 替换期间自己直接请求目标插件的 fork                       | 否       | 否       | 否       |
| 替换期间新建、请求源插件的 fork；被替换的父节点新建的后代 | 是       | 是       | 是       |
| 被后来的 `replace`/`restart` 接管的 fork 及其后代         | —        | 退出判定 | 否       |
| 依赖它的普通消费者                                        | 随之重启 | 否       | 随之重启 |

别名恢复会保留后来操作已经接管的写入（`aliases.ts:193-230`）。

### 1.3 两族为什么不能混用

| 冲突                                                                                                   | 位置                                                                                          |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 托管 fork 禁止图解析的依赖和 `retry`；重启族依赖二者                                                   | `core/src/internal/transition.ts:670-680`                                                     |
| `replace` 按插件身份改全局别名；转换只改一个 fork 的路由                                               | `core/src/Graft.ts:590`、`core/src/internal/aliases.ts`                                       |
| 转换要求 `overlap: true`；重启族从不重叠                                                               | `core/src/internal/transition.ts:376`                                                         |
| 重启撤回发布、消费者随之重启；转换保持门面，消费者不必重新获取服务（调用仍受准入、路由与执行结果影响） | `core/src/internal/activation.ts:237-280`、`transition.ts:610-650`                            |
| 配置：重启族有 `Fork.update`；转换族把配置放在候选里                                                   | `core/src/Graft.ts:280`                                                                       |

| 能力：托管直连只支持一元契约、受限注入、有限并发；安装信任策略后，普通与 runner 部署被拒绝             | `plugin-remote/src/internal/transition.ts:410-425`、`plugin-remote/src/host/index.ts:211-218` |

### 1.4 真正重复的部分

审查后剔除了合理的分层（持久化投影、持续状态、错误通道不算重复）。真正重复的是控制流程：

| 机制         | 实例                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------- |
| 恢复控制流程 | `replace` 的别名与 spec 还原；转换的 `recover`；HMR 的 `restoreEntries`；发布的逆序补偿                       |
| 一次性结果   | `ReplaceResult`、`WatchResult` 中的回滚类变体、`Transition.Outcome`；`Fork.update`/`restart` 没有结果         |
| 期限         | `replace` 的单一可选超时、恢复不限时；转换的总预算与预留；Remote 的关闭期限；Loader 与 `Fork.update` 没有期限 |
| 串行化       | revision 接管；全局 `transitionBusy`；Loader 的信号量与队列；HMR 的 `serial`                                  |

## 2. 目标模型

### 2.1 名词

| 名词                  | 含义                                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| **期望配置**          | 一个逻辑实例应当运行什么：代码（插件定义或制品）、原始输入、放置、realm、intercept、依赖声明。不可变  |
| **输入快照**          | 某次准备时解析得到的输入，例如已解析的环境引用。Loader 重试会重新解析，所以原始输入不变不代表快照不变 |
| **激活绑定**          | 一代启动时取得的依赖服务、租约与权限。每次新建一代都重新获取                                          |
| **候选**（Candidate） | 期望配置 + 输入快照；转换的目标                                                                       |
| **变更**（Change）    | 一次有稳定身份和所有者的操作：一组选择器、按成员规则展开的 fork 集合、每个 fork 的意图                |
| **策略**（Strategy）  | 一个 fork 从旧候选到新候选的执行方式：`InPlace`、`Restart`、`Overlap`，将来 `Handoff`                 |
| **结局**（Outcome）   | `Accepted`、`Aborted`、`Recovered`、`RecoveryFailed`、`Stuck`；批次结局另带每个成员的结局与残留状态   |

恢复时：期望配置用旧的；输入快照**重新解析**（例如轮换后的凭据），并重新通过信任检查；激活绑定总是重新获取。旧候选不是永久有效的恢复授权。

### 2.2 成员规则：四个集合

把选择器展开成「一张 fork 清单」不足以保留 1.2 的规则。每个变更维护四个集合，并允许在执行期间动态加入：

| 集合   | 用途                 | 例                                              |
| ------ | -------------------- | ----------------------------------------------- |
| 选中   | 应用新候选           | 运行源插件的 fork                               |
| 受影响 | 协调停止、启动与租约 | 依赖消费者、子 fork                             |
| 判定   | 决定接受还是恢复     | 选中且替换前健康的 fork；被替换父节点新建的后代 |
| 恢复权 | 失败时由本变更恢复   | 尚未被后来的变更接管的成员                      |

每个 fork 记录它由哪个变更创建（来源信息，今天的 `Spec.requested`
是其中一种）。归属不靠「现在运行哪个候选」推断。

**接管**：v0.1 说「不保留」，同时又说「保留 `replace`
的细节」，二者矛盾。本版的选择是**冲突时拒绝**（`Busy`），这是一项有意的语义删除；但仍然保留 revision/fencing，防止迟到的结果覆盖较新的状态。

### 2.3 策略选择：按意图，不按轻重

不设全局的轻重顺序。`InPlace`
可能改外部系统、局部修改内部状态，不一定比重启风险小；`Overlap`
可能重复执行定时任务、争用端口或独占资源。选择规则是「请求意图 × 允许的策略 × 适用条件」：

| 意图     | 默认策略                  | 适用条件                                                       | 失败时                                       |
| -------- | ------------------------- | -------------------------------------------------------------- | -------------------------------------------- |
| 改配置   | `InPlace`                 | 当前这一代的 `apply` 返回了 `Update`（运行时值，不是静态能力） | 退回到调用方允许的下一种策略，并记录在证据里 |
| 显式重启 | `Restart`                 | 无（不会被优化成 `InPlace`）                                   | —                                            |
| 改代码   | `Overlap`，否则 `Restart` | `Overlap` 要求插件声明 `overlap`、经门面提供服务、驱动支持     | —                                            |
| 依赖失效 | `Restart`                 | 必须重新获取 Context；`Update` 替换不了已捕获的服务            | 不可拒绝，见 2.6                             |

`InPlace` 不产生新的一代，只更新这一代的配置版本。

### 2.4 期限与终止证据

期限只约束**协调器等多久**，不保证执行已经停止。必须区分「等待期限到达」和「得到终止证据」：

| 放置           | 终止保证                                                                     | 超时后                                                                                                                      |
| -------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Worker、子进程 | 硬终止，有退出证据                                                           | 强制终止，等退出证据                                                                                                        |
| 进程内         | 只有合作式：中断 `apply`、撤回、等租约释放、关闭 Scope，这些等待都可能不结束 | 进入隔离：保留清理 fiber 的所有者、租约和失败 cause，禁止相冲突的新启动；迟到完成时解除隔离；宿主最终关闭时由运行时负责收尾 |

所以 `Restart`
并非「无前提」：它要求可以取得停止证据，或者接受隔离后的资源冲突规则。生命周期操作沿用转换引擎今天的做法，放进有归属的 fiber 再限时等待（`transition.ts:280-298`）。同步阻塞事件循环的代码连
`Stuck` 也无法按时报告，这一点要写进文档。

### 2.5 并发：冲突域，不是全局锁

按 fork 加锁不够：兄弟 fork 可以通过同一 realm 的服务租约相互依赖；两个新增可能争用同一个服务槽；两次替换可能共用一个别名家族。

| 冲突域   | 两个变更何时冲突                       |
| -------- | -------------------------------------- |
| fork     | 选中或受影响的集合相交                 |
| 服务槽   | 撤回或发布同一 realm 中的同一个键      |
| 依赖边   | 一方的撤回需要等另一方持有的消费者排空 |
| 部署组   | 共用执行单元，新旧两种分组都要算       |
| 别名家族 | 改写同一插件身份的解析                 |

实现上用局部锁加事务内校验与失效通知，不锁整个传递闭包；但锁的顺序、冲突判定和失效处理要先写清楚。`Stuck`
只封锁它的冲突域，其中包括仍持有它租约的消费者。

### 2.6 监督：留在 fork 里，用转换执行一次尝试

监督不能只是「外部发起一个请求」：

- 依赖失效不能被拒绝。服务撤回后，消费者必须停止使用旧依赖；如果请求因 `Busy`
  被丢弃，旧激活会一直活着，挡住提供方的排空。
- `retry`
  有跨尝试的状态。今天的调度绑定 spec 与依赖快照，连续失败复用同一个 step；每次重建调度会重置次数和退避。

所以：**supervisor 留在 fork 的长期 Scope 中**，持有期望状态和调度状态；转换只负责执行一次尝试。依赖失效走一条不可丢失的失效协议，并定义它与在途变更之间的合并或抢占规则。

### 2.7 别名：先定线性化点

今天别名与 spec 在变更开始时一起改写，之后新建的 fork 立即解析到新定义。v0.1 提议「接受时再提交别名」，会带来：转换期间加载旧身份仍得到旧定义；新候选启动时加载的子插件可能拿到旧版本；并发注册的 fork 漏出清单；没有任何现存 fork 时，别名变更本身仍有意义。

本版不移动提交点，先列出三个选项，留待决定（第 6 节问题 2）：

| 选项                                 | 代价                                       |
| ------------------------------------ | ------------------------------------------ |
| 开始时提交（今天的语义），恢复时还原 | 失败的版本会短暂对新加载可见               |
| 变更内暂存解析视图，接受时提交       | 变更内与变更外看到的定义不同，需要定义边界 |
| 冲突的加载等待变更结束               | 加载可能被阻塞到预算上限                   |

### 2.8 取消、所有权与观察

统一结局之前，先统一这三件事：

| 动作            | 语义                                                                               |
| --------------- | ---------------------------------------------------------------------------------- |
| 提交            | 变更被准入后，由运行时（而不是调用方）拥有，获得稳定的身份                         |
| 等待            | 调用方等待结局；取消等待不取消变更                                                 |
| 请求取消        | 显式操作；在不可逆点之前有效，之后被拒绝                                           |
| 释放（dispose） | 关闭准入，再取消已准入的变更；结局保留被中断的阶段与证据                           |
| 观察            | 按身份查询或订阅结局；复用 `generations` 与 `generationEvents`，不另造持久化工作流 |

所有迟到的失败 cause 都要有归属。

### 2.9 Loader 的持久化

| 来源               | 规则                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------- |
| 外部编辑           | 文件已经落盘，视为一个已存在的期望版本；失败后保留磁盘上的意图，报告它与运行态的差异          |
| 命令编辑           | 明确基于哪个存储版本，准备阶段保留比较并交换（CAS）信息（`Include` 今天已用期望文本保护写入） |
| 运行成功、写入失败 | 结局必须写明，并定义重启后以谁为准                                                            |
| 跨崩溃一致         | 需要持久化的意图与提交协议；只把写入挪到接受之后不够                                          |

### 2.10 开发变更：发布流水线的开发配置

**决定（2026-11-07）：HMR 不再维护自己的变更路径，而是成为发布流水线的开发来源。**
开发与生产共用同一条流水线，只在「构建候选」和「记录」两个阶段用不同的实现。

理由：

| 理由                         | 依据                                                                                                                                                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 两条路径已经互斥             | 运行时里只要有一个托管 fork，整个应用的 HMR 就返回 `Skipped("managed-fork")`（`hmr/src/index.ts:692`）。用了生产升级路径，就失去开发时的热重载                                                                                              |
| HMR 最难的限制来自进程内替换 | 长时间开发内存没有上限（Node 的 ESM 缓存不回收版本化模块）；CommonJS 与原生依赖需要重启；别名与身份冲突导致的 `Skipped`（`hot-reload.md`「Limits」）。按单元换代时，旧 isolate 随单元终止回收，子进程放置不受模块格式限制，换代不改全局别名 |
| 开发与生产要走同一条路       | Erlang 开发用 `l(Mod)`、生产用 relup，relup 平时无人运行，到生产才第一次真正执行，这是它难测的重要原因（推断）。开发时按插件的生产放置与策略换代，「重叠运行不安全」「探针写错」在开发阶段就会暴露                                          |

一条流水线，两种配置：

| 阶段     | 发布配置                                             | 开发配置                                   |
| -------- | ---------------------------------------------------- | ------------------------------------------ |
| 来源     | 发布源文件                                           | 监听到的文件变化；连续的编辑合并成一个变更 |
| 构建候选 | 捕获内容寻址的目录，校验摘要                         | 直接引用工作目录，或只做快速哈希；不复制   |
| 计划     | 校验字节、绑定、来源与运行时要求，解码配置，比较差异 | 比较差异、解码配置                         |
| 应用     | 转换（第 2.2–2.8 节）                                | 同一个转换；策略与放置取插件在生产中的设置 |
| 预算     | 发布的默认值（trial 2 秒）                           | 运行探针；trial 默认为零                   |
| 记录     | fsync 后原子替换的日志、信任审批、撤销清单           | 只在内存中                                 |
| 结局     | `Transition.Outcome`                                 | 同一个结局                                 |

约束：

- **开发配置不能进入生产。**
  开发候选没有制品身份，也没有审批记录；安装了信任策略的应用拒绝开发配置。
- **锁分离保留。** 今天 HMR 在等待激活时刻意释放导入器的
  `serial`，否则新插件启动期间的导入会被堵住。开发来源同样把「收集编辑」与「执行变更」分开：变更遇到
  `Busy` 或失败时，累积的编辑保存下来，等当前变更结束后再调度。
- **宿主代码另算。**
  按「插件运行在与内核隔离的单元中」的方向，宿主进程里只剩内核与少量宿主插件（如网关），它们很少改动。倾向于改了就重启进程（第 6 节问题 7）。

**延迟（已决定，2026-11-07）：开发时慢一些可以接受。**
比较的基准是重启整个进程，不是今天的增量重载：按单元换代只重启变化的插件，其余插件与会话保持运行，所以总是比全部重启快。开发配置不以追赶增量重载的速度为目标。仍然记录从保存到新代码开始服务的时间，用来发现退化；预热 Worker、跳过目录复制等优化只在确有需要时再做。

## 3. Scale 的准确表述

改成变更集并不会缩小**必要的**影响范围：按插件身份替换，本来就可能跨所有租户；重启一个被所有插件注入的提供方，本来就会影响所有消费者。所以承诺写成：

> 开销与中断随必要的受影响集合增长，不随无关的插件和租户增长。

要兑现它，需要：选择器支持实例与 realm 范围；维护局部索引，替代今天替换与托管查找中的运行时级扫描（`replacement.ts:94-118`、`transition.ts:1057-1068`）；用稳定门面切断不必要的重启传播。

## 4. 删除清单与对应的不变量

每一项写明它保护什么、替代机制在哪里保证同一性质。没有替代机制之前不删。

| 删除                                                                                                               | 它今天保护的性质                   | 替代机制与线性化点                                       |
| ------------------------------------------------------------------------------------------------------------------ | ---------------------------------- | -------------------------------------------------------- |
| `ManagedFork`（`Fork.update`/`restart`、`replace`、Loader、HMR 中的检查）                                          | 绕行写入不与协调器竞争同一个 fork  | 冲突域准入（2.5），在变更准入的事务中                    |
| `withUnmanaged`、`assertUnmanaged`                                                                                 | 外部写入与驱动注册不交错           | 驱动注册本身作为一个变更，经同一准入                     |
| 托管注册对 `retry`、图解析依赖的禁令                                                                               | 激活循环不在协调器背后自行重启     | 监督留在 fork 内，经转换执行尝试（2.6）                  |
| `ReplaceResult`、回滚类 `WatchResult`                                                                              | —（纯重复）                        | 统一结局 + 成员结局（2.1）                               |
| 四份恢复控制流程                                                                                                   | 失败后回到可用配置                 | 统一恢复流程；各参与者保留自己的恢复逻辑（如发布的日志） |
| 全局 `transitionBusy`/`transitionStuck`                                                                            | 同时只有一个转换，避免未定义的交互 | 冲突域准入；`Stuck` 只封锁其冲突域                       |
| Remote 的两种入口                                                                                                  | —                                  | 统一入口；**保留**能力检查、制品身份要求与信任准入       |
| `plugin-release` 的成员与放置限制                                                                                  | 发布只做转换支持的事               | 变更支持新增、移除、形状变化后再放开                     |
| HMR 的进程内重载机制：版本化模块 URL、导入者闭包的不动点、导出身份匹配、条目表还原、`WatchResult` 与四种 `Skipped` | 在同一进程里安全地替换模块         | 开发配置按单元换代（2.10）；随插件迁入独立单元逐步删除   |

不删除：期限、唯一所有者、租约排空、信任检查。它们是规则，不是保护。
