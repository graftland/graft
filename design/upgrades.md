# 网络透明的插件与生产热升级：架构设计

状态：v8，2026-11-07，已定稿为目标架构，进入实现。本文不是站点文档，不受
`packages/docs/STYLE.md` 约束。

**v8 的价值导向决定**（依据 [`value.md`](value.md) v2，用户已采纳）：

| 决定     | 内容                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 定位     | Graft 是面向长期运行的 TypeScript 应用的 Effect 原生插件运行时：以可控的影响范围更换任何能力，并如实知道结局                        |
| 首发人群 | 运行常驻机器人或集成网关的小团队，扩展由他人维护，上游会话代价高                                                                    |

| 配置发布 | 写明版本化范围；密钥以引用出现；撤销不被回滚恢复；机群发布交给现有工具（`value.md` 4.3）                                            |
| 连续性   | 分为传输、会话、进行中操作、状态四层；切片 1 只保证传输连续（`value.md` 4.4）                                                       |
| 投影     | 契约投影是带注解的子集（`value.md` 4.5）                                                                                            |

方向决定（用户，2026-11-07）：

- **Remote 是核心能力，每个插件都是远程插件。**
- **插件运行在与内核隔离的执行单元中**，默认是 Worker。
- **保留本地模式**：需要共享连接池等无法编码的资源时，几个插件可以组成一组，共用一个执行单元。
- **契约模型从第一性原理重新设计。**

v7 吸收了对 v6 的两轮审查：一轮是协议一致性审查，一轮是对网络透明、契约和本地模式的独立审查。审查历史见附录。

## 0. 原则与保证

### 0.1 原则

| 原则                   | 含义                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **位置透明，失败显式** | 插件代码不随运行位置改变。延迟、部分失败、取消、编码这些网络事实，在每个调用的类型里都显式可见，**物理上同处一地时也一样**：调用移到别处，别名、取消和重试的安全性都不会悄悄改变。 |
| **单元之间不共享内存** | 跨执行单元的交互一律是经过编码的调用，线上表示与放置位置无关。共享只发生在声明过的部署组内部。                                                                                     |
| **内核不运行插件代码** | 主线程只运行 Graft 内核：协调器、快照、执行票据账本、单元之间的连接建立。插件代码和契约代码只在执行单元里运行。                                                                    |
| **回收靠终止**         | 每个单元代都是一个执行单元。丢弃这一代，就是先导出它的状态，再终止这个单元。                                                                                                       |
| **Effect 原生**        | 契约就是 Effect 的 `Rpc`、`RpcGroup` 和 Schema 值；资源归 `Scope`，执行归 fiber。Effect 缺少的能力向上游提出，Graft 不自行绕过。                                                   |

### 0.2 保证

保证只在**声明的容量和截止时间之内**成立。

| 保证             | 精确含义                                                                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 不丢已入场的工作 | 已入场的操作要么在它钉住的快照上执行完毕，要么以明确的失败结束，失败信息会说明执行是「确定未被接纳」还是「结果未知」。                                               |
| 切换窗口内不拒绝 | 切换窗口内到达的请求在入场队列中等待。准备阶段与旧代重叠，可以缩短窗口，但窗口不会消失。超出容量或等待上限时，给出声明的过载响应。                                   |
| 状态延续         | 声明了交接状态的实例，状态先导出、再迁移，交给新的服务尝试。只有在导出完成之前单元被强制终止时，状态才会丢失，此时如实报告。                                         |
| 最小变化闭包     | 换代的只有以下几类：本身发生变化的实例；与它同在一个部署组里的实例；它所需的契约操作受影响的消费者。闭包在新旧两种分组上计算到不动点。跨单元的依赖不会引起连带重启。 |
| 截止             | 插件的每个阶段都有截止时间，超时就终止对应单元。Worker 的终止是「尽快」，不是一个固定上限。原生代码卡住、runner 断连且租约未到期时，结局是 `Stuck`。                 |
| 回收             | 单元代退役时随单元终止而回收。在终止之前，存活的单元、候选、试运行中的旧代都要占用容量，这部分由第 12 节约束。                                                       |
| 可回滚、可恢复   | 越过 PONR 之前可以回滚；PONR 在派发任何不可逆动作之前持久化；崩溃后按日志恢复。                                                                                      |

故障域：Worker 隔离 isolate，但与内核共享同一个进程。进程级崩溃（原生代码出错、进程内存耗尽）会影响整个进程。需要隔离这类故障时，使用子进程放置。

## 1. 运行结构

```
 graft start（进程）
 ├─ 主线程：内核
 │   ├─ 协调器（转换、日志、PONR、权限纪元）
 │   ├─ 快照与注册表索引
 │   ├─ 执行票据账本
 │   └─ 单元连接的建立与授权
 ├─ Worker：插件实例 A 的单元
 ├─ Worker：部署组 billing {连接池 P, 插件 D, 插件 E}
 ├─ Worker：入口插件（HTTP 监听）
 ├─ 子进程：插件实例 B
 └─ 连接：runner 上的插件实例 C
```

| 执行单元 | 隔离                                       | 何时使用                                     |
| -------- | ------------------------------------------ | -------------------------------------------- |
| Worker   | 独立的 isolate、模块图和事件循环；共享进程 | 默认                                         |
| 子进程   | 独立进程                                   | 原生模块、CommonJS、进程级故障隔离、资源限制 |
| Runner   | 另一台机器或容器                           | 硬件、数据就近、权限边界                     |

- 执行单元的种类就是放置方式，写在配置里。同一个插件制品可以放进任何一种单元。
- 每个单元运行一个普通的 Graft 运行时，通过**引导通道**与内核通信。引导通道很小：Worker 用
  `MessagePort`，子进程用 stdio，runner 用 Remote 已有的连接。部署控制协议（第 9.3 节）在引导通道上运行。传输插件提供的是更高层的通道。一方传输插件与第三方传输插件遵循同一条规则。
- **数据通道直连。** 内核为实际存在的依赖边建立单元之间的直接通道（同一进程内用
  `MessageChannel`，跨进程用传输插件），并把通道绑定到快照和服务尝试。内核负责授权和计账，不转发业务载荷。内核转发保留为一种可选的传输方式。
- **内核不导入插件模块。** 规划所需的声明由候选单元经 `Describe` 返回。
- **环境服务按单元提供**，例如
  `FileSystem`、`HttpClient`、时钟、日志。intercept 必须是可序列化的配置，或者在受影响的单元里加载的代码；任意闭包不能被远程继承。

## 2. 部署组与本地服务

### 2.1 规则

| 概念     | 规则                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 本地服务 | `inject` / `provides` 中的普通 `Context.Service` 键。值不经编码，原样传递。                                                                            |
| 部署组   | 共享一个执行单元的一组实例，**由运维在配置中声明**（`group: billing`）。没有声明时，计划会把本地服务连通的实例推导成一个组，作为默认值并在计划中显示。 |
| 约束     | 本地服务的提供方与注入方必须在同一个组。违反时计划报错，并给出完整的依赖路径。                                                                         |
| 解析顺序 | 先按 realm 解析出具体的提供方实例，再根据解析结果推导本地边。两个租户在不同 realm 中发布同一个键，不会因此被合并。                                     |
| 放置     | 一个组只有一个放置。成员显式要求的放置互相冲突时，计划报错；未声明的默认值不算冲突。                                                                   |
| 双重身份 | 既需要被本地使用、又需要被远程访问的资源，导出两个接口：本地服务，以及建在它之上的契约门面。本地使用者加入资源所在的组，远程使用者不加入。             |

### 2.2 组的三种策略

| 策略       | 规则                                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| 共址       | 交换原始引用的实例必须在同一个单元里。                                                                       |
| 整体换单元 | 组内任一成员变化，都会为整个组准备一个新单元。这是因为回收代码的唯一方法是终止 isolate。                     |
| 失败重启   | 成员的普通 Effect 失败只按组内的依赖关系重启相关成员，不会连带无关成员。只有单元崩溃或被终止时，才影响整组。 |

**闭包计算。** 变化闭包要同时在**旧分组和新分组**上计算，直到不动点：

- 组被拆分时，仍住在即将退役的旧单元里的成员必须一起换代；
- 组被合并时，原来的几个组整体进入闭包，合并到一个新单元；
- 可选本地依赖的出现或消失，本身就是一次分组变化。

实例身份与单元身份互相独立。

**单元内的所有权仍然需要拆分。**
同一个单元里，同一个本地提供方可能同时被准备段和服务段租用。两段的租约必须是不同的所有者：释放服务段的租约，不能连带释放准备段的租约。今天按 fork
id 记录的租约（`activation.ts:365`）以及每个图节点只有一个 resolution（`runtime.ts:33`），都必须先拆开。组内某个成员重试时，新的服务尝试也要经协调器发布，不能在单元内部私自改路由。

本地模式是一种显式的取舍：换代范围更大，故障域也被共享。计划会列出每个组的成员，以及每个成员入组的那条依赖边。

## 3. 契约

### 3.1 要求

| 要求           | 原因                                                                         |
| -------------- | ---------------------------------------------------------------------------- |
| 放置无关的语义 | 同一个值，无论单元在 Worker、子进程还是 runner 上，含义都必须相同。          |
| 独立演进       | 提供方和消费方在不同单元中分别升级。                                         |
| 粒度合适       | 新增一个操作不应强迫所有不相关的操作一起改变身份。                           |
| Effect 原生    | 契约就是 Effect 的 `Rpc` / `RpcGroup` / Schema，不在 Graft 里再包一套。      |
| 只描述接口     | 不含部署事实，也不含实现。                                                   |
| 失败显式       | 业务错误与系统失败分开；系统失败要说明发生在哪个阶段，以及执行是否已被接纳。 |
| 第三方平等     | 任何包都可以定义契约，内核不对任何契约做特殊处理。                           |

### 3.2 模型：不可变的操作，可组合的契约

**操作和事件是不可变的协议单位**，每个都有自己的身份
`name@version`。**契约**是这些单位组成的一个具名集合，用于组织代码和类型。

```ts
// @acme/pricing-contract — ordinary Effect values plus Graft identity metadata.
export const quote = Contract.operation(
	"@acme/pricing/quote",
	1,
	Rpc.make("quote", {
		payload: Cart,
		success: Quote,
		error: PricingError,
	}),
)
export const watchRates = Contract.operation(
	"@acme/pricing/watchRates",
	1,
	Rpc.make("watchRates", {
		payload: Region,
		success: Rate,
		stream: true,
	}),
)
export const ratesChanged = Contract.notification(
	"@acme/pricing/ratesChanged",
	1,
	RatesChanged,
)

export const Pricing = Contract.bundle("@acme/pricing/Pricing", [
	quote,
	watchRates,
	ratesChanged,
])
```

| 方面   | 规则                                                                                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 身份   | 每个操作或事件都有 `name@version`，一经发布就不可变。不可变的范围包括 Schema、变换、默认值、精炼、解析选项、错误的含义，以及编解码依赖。 |
| 演进   | 任何线上变化或语义变化都会产生一个新版本的**这个操作**，其他操作不受影响。新增错误变体也算协议变化，除非原协议明确允许未知变体。         |
| 契约   | 只是操作的集合。新增操作不会改变已有操作的身份。                                                                                         |
| 消费方 | 注入一个契约，或者契约的一部分。计划根据它实际用到的操作身份，检查是否有提供方提供，判断方式是精确的集合包含。                           |
| 提供方 | `Contract.implement(bundle, handlers)`。一个提供方可以同时实现同一操作的多个版本；旧版本的实现通常是新实现之上的一层普通代码。           |
| 底层   | 就是 Effect 的 `Rpc` 与 `RpcGroup`。Graft 只附加 Effect 本身不表达的东西：身份、版本，以及通知的元数据。                                 |

### 3.3 可移植的线上表示

Schema 可以把**解码后的类型**表达得很丰富（类、品牌类型、`Map`、`DateTime`
等等），但跨单元传输的**线上表示**只有一种，与放置方式无关：

- 线上表示由 Effect RPC 的序列化编解码机制选择：JSON 用 `Schema.toCodecJson`（见
  `RpcSerialization.ts:22`），MessagePack 对同一个模型做二进制编码。Worker 之间传输的也是这个编码结果，而不是原始的
  `Encoded` 结构化克隆。这样，一个值在 Worker 里能传，换到子进程里也一样能传。
- 自定义声明如果在这个表示中没有对应的编解码器，就不能用在契约里。这条检查在计划阶段对契约中的 Schema 进行。
- 禁止出现在线上的值：`SharedArrayBuffer`、可执行对象、传输句柄。
- 二进制数据：只有传输层自己拥有的缓冲区可以转移所有权，调用方的缓冲区先复制再转移（与 Remote 现有的
  `workerChannel.ts:39` 一致）。

这一条与已经撤销的「契约是无损 JSON 文档」不同。契约仍然是可执行的 Effect 值，Schema 的能力完整保留；这里约束的只是传输承诺能运载什么。

### 3.4 来源与一致性

同名同版本的两份构建，可能都解码成功，却对同一个值有不同的理解。例如一边把整数当作「分」，另一边当作「元」。仅靠读时校验发现不了这类问题。所以：

- 清单记录每个操作身份的来源，也就是契约包的构建身份。同一个身份出现两个无法解释的不同定义时，计划拒绝。摘要只用来核对来源，不用来证明兼容。
- 线上变换应当是确定的，不依赖时区、配置或外部状态。如果编解码依赖服务（Schema 的
  `R`），双方单元都必须声明并满足这些依赖。
- 契约包附带一致性夹具：请求、响应、错误和流的样例值。不同的构建可以用它们互相检验。

### 3.5 绑定

- 注入得到的客户端是一个**逻辑能力**：每次调用时，按调用方操作所钉住的快照解析到某个服务尝试。客户端在
  `serve` 时被捕获，也不会因此永久绑定到当时的提供方。
- 每次调用一旦派发，就绑定到一个服务尝试，直到这次调用结束。流在整个生命周期内保持同一个绑定，绝不会中途换成别的版本。
- 删除某个操作版本之前，既要确认未来没有绑定需要它，也要确认已经没有仍钉着它的存活操作或流。
- 断开的流不会自动续接。需要续接时，由领域协议定义游标、重放和去重。

### 3.6 失败模型

```ts
class ContractFailure extends Schema.TaggedError<ContractFailure>()(
	"ContractFailure",
	{
		reason: Schema.Literals([
			"Unavailable",
			"Transport",
			"Protocol",
			"Deadline",
			"Overload",
		]),
		phase: Schema.Literals(["Admission", "Request", "Execution", "Response"]),
		outcome: Schema.Literals(["NotAdmitted", "Unknown"]), // never inferred as safe to retry by tag alone
		cause: Schema.Defect(),
	},
) {}
```

- 业务错误保持各自的类型。中断与缺陷仍然是 Effect 的 `Cause`，不放进错误联合。
- `outcome`
  是唯一可以用来判断重试是否安全的依据。例如，提供方已经完成扣款，但响应编码失败：这是
  `Protocol` 加 `Unknown`，不能重试。
- **上游需求。** Effect RPC 今天在编码载荷和解码响应时都用
  `orDie`（`RpcClient.ts:737`、`RpcClient.ts:820`），服务端会把编码失败转换成格式化后的缺陷（`RpcServer.ts:823`）。因此无法在外层可靠地还原出结构化的
  `Protocol`
  失败。需要向 Effect 提出：提供带阶段信息、保留诊断内容的结构化编解码失败报告。在此之前，这一项标记为未实现，不通过解析错误字符串来绕过。

### 3.7 支持的 RPC 子集

首批支持一元调用和服务端流。延迟回复、discard、notification 这三种请求模式暂不支持：延迟回复会在请求生命周期之外再派生一个 fiber（`RpcServer.ts:379`、`RpcServer.ts:424`），使完成确认无从界定。要支持它们，需要 Effect 先提供完整的逻辑请求生命周期钩子。这一项作为上游需求提出。

### 3.8 备选方案

| 方案                           | 为什么不选                                         |
| ------------------------------ | -------------------------------------------------- |
| 契约只存在于 TypeScript 类型中 | 跨边界的值无法校验                                 |
| 推导 Schema 之间的兼容性       | 不可靠，并且把语义变化误当成结构问题               |
| 整个契约共用一个版本号         | 无关操作被迫一起改变身份，导致冗余的适配和部署耦合 |
| 按字段做版本                   | 引起组合爆炸，而且解决不了语义兼容问题             |
| Worker 内传原始结构化克隆      | 结果依赖放置位置，还可能共享内存                   |

## 4. 交互形式

现有的「事件」混合了几种不同的交互。v7 把它们拆开：

| 形式       | 是什么                                                                       | 跨单元方式                                                         |
| ---------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 通知       | 事实。带载荷，没有结果                                                       | 契约通知：同一发出方对同一订阅者按顺序投递；投递失败返回给发出方   |
| 查询与扇出 | 需要结果的分发：今天的 `bail`、`parallel`、`settle`                          | 契约操作，聚合方式写明                                             |
| 中间件     | 环绕下游执行：今天的 `waterfall`，先后处理、共享首次执行、跨 `next` 持有资源 | **只在单元内**：与它所属的协议适配器放在一起，用普通的 Effect 组合 |

- 远程中间件需要一套真正的续体协议，包括调用范围内的 `next`
  端点、清理、重入和失败处理，复杂度很高。不作为默认形态；只有当它确实是产品需求时才单独设计。
- 一个通知的多个版本：发出方同时发布这些版本，或者提供显式的适配器。同一次事件发生产生多个版本时，各版本带同一个发生 id。
- 在操作或调用中注册的订阅**只在本操作内有效**，随操作 scope 关闭，不进入快照，也不对其他操作可见。

### 4.1 注册表：数据 + 端点，由所有者解释

```ts
const Routes = Snapshot.registry("@graftland/plugin-http/Routes", {
	contribution: RouteDescriptor, // data, encoded with the portable representation
	endpoint: HttpHandler, // the contract the contributor implements
})
```

注册表的**所有者单元**负责解释贡献，并保留原生组合能力。贡献本身只携带描述和端点引用。

| 功能   | 所有者单元内                          | 跨单元边界                                                                                                                         |
| ------ | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| HTTP   | 原生 `HttpRouter`、中间件、请求上下文 | 流式 HTTP 桥：请求体与响应体双向流控、取消、请求元数据、清理所有权。WebSocket 等协议升级需要双工会话；不需要时，与监听器放在同一组 |
| CLI    | 原生 `effect/cli` 命令树、帮助、补全  | 命令描述加调用端点；终端与 stdin/stdout/stderr 作为显式能力；文件路径是谁的文件，由文件能力说明                                    |
| MCP    | 工具集、自定义种类的安装逻辑、补全    | 工具描述加调用端点；客户端回调与会话能力用显式代理                                                                                 |
| 第三方 | 自定义校验与派生                      | 同上                                                                                                                               |

原始平台对象（请求的 source、multipart 的临时路径）只在所有者单元内有效。

**第三方平等的验收示例**（全部只通过公开 API 完成）：

- 自定义注册表；
- 实现入场与取消的监听器；
- 带动态可见性和补全的 MCP 种类；
- 传输与认证的组合；
- 提供契约门面的本地原生资源。

## 5. 核心模型

### 5.1 身份与所有权

| 对象     | 是什么                                             | 持有                                         |
| -------- | -------------------------------------------------- | -------------------------------------------- |
| 实例     | 部署图中的逻辑插件实例                             | 交接状态、契约槽位、任期高水位、历史         |
| 单元代   | 一个执行单元，承载一个实例或一个部署组             | 单元本身                                     |
| 代       | 单元代中的一个实例：定义、配置，以及一次 `prepare` | 准备 scope、准备期租约                       |
| 服务尝试 | 一代中的一次 `serve`，带一个新任期                 | 服务 scope、任务、贡献、独占资源、服务期租约 |
| 操作     | 一个入场的工作单元                                 | 执行票据                                     |

- 单元代是所有权图中的一个节点。只有当它的**所有成员**都完成了执行、租约、状态导出和保留义务之后，单元代才能终止。个别成员的准备 scope 可以先关闭，但只要还有成员需要这个单元，单元就继续存活。
- 任期高水位在授予所有权**之前**写入日志，作为 fencing token。
- 实例身份来自三处：Loader 配置项的
  `id`；父实例身份加上声明名；代码直接加载时的显式命名。
- 所有权图有两种投影：启动图和退役图。两者都覆盖单元代、代、服务尝试、租约和结构归属。

### 5.2 快照：安装与激活分开

快照是内核持有的不可变索引：记录注册表中的贡献、契约操作 → 服务尝试的路由，以及配置和拓扑。快照本身不持有资源。

发布的屏障需要满足以下不变式：

1. **安装不等于激活。**
   单元按快照 id 保存视图和派生结果。未变化的所有者单元为候选快照派生路由表时，不覆盖正在使用的路由表。
2. **确认要精确。**
   每个确认都指明单元代、快照 id 和准备结果；已退役单元迟到的确认不计入新的屏障。
3. **入场由内核原子决定。**
   内核在授予操作时选定并钉住一个快照；单元不能拿自己最近安装的快照自行入场。
4. **暂存路由先于使用。**
   候选的生命周期调用需要的路由先安装；然后冻结贡献、派生、确认，最后提交。派生不等待业务入场，也不等待自己的发布。
5. **部分确认只中止暂存。**
   未变化的所有者单元不受影响。提交之后某个参与方失败，表现为显式的不可用；各单元不会自行回退路由。
6. **回收跟随执行所有权。**
   中止候选或退役旧快照时，只释放与之对应的暂存视图和资源。

### 5.3 三个谓词

| 谓词     | 成立条件                                                               | 用途                 |
| -------- | ---------------------------------------------------------------------- | -------------------- |
| 执行静默 | 受影响的服务尝试上，不再有任何未完成的执行票据（包括后代票据和终结器） | 何时可以停止服务尝试 |
| 资源退役 | 退役图中依赖这些资源的租约都已结束，状态已导出并被确认                 | 何时可以终止单元     |
| 保留     | 哪些代和单元代留作回滚之用，前提是满足保留资格（第 8.5 节）            | 回滚的快速路径       |

### 5.4 协调器与权限纪元

整个应用只有一个协调器，同一时间只执行一个转换，**包括试运行期**。协调器的权限带有一个**权限纪元**，写在日志里。任期分配、入场授权、快照发布都必须携带当前纪元；纪元过期的请求一律被拒绝。内核交接时，纪元随之转移（第 10.2 节）。回滚以补丁转换的形式进行。

## 6. 插件编写模型

```ts
Plugin.make({
	name: "@acme/checkout",
	config: CheckoutConfig,
	prepare: {
		inject: [PgPool],
		run: (config, { pgPool }) => Rates.load(pgPool),
	},
	inject: [PgPool, Pricing.pick(quote)], // local service + the contract operations actually used
	provides: [Checkout],
	children: [{ name: "ledger-compactor", plugin: Compactor }],
	state: Ledger,
	serve: (rates, { pgPool, pricing }, ledger) =>
		Effect.gen(function* () {
			yield* Contract.implement(
				Checkout,
				makeCheckout(pgPool, rates, pricing, ledger),
			)
			yield* Plugin.fork(consumeOrders(pgPool, ledger))
		}),
	overlap: false,
})
```

| 规则                  | 内容                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------- |
| `apply`               | 等价于不带 `prepare` 的 `serve`                                                                      |
| `inject` / `provides` | 契约操作、契约或其子集、注册表贡献、本地服务                                                         |
| 准备期依赖            | 提供方在变化闭包中时，该实例进入后准备波次；启动图交错调度，环在整张图上检测                         |
| `serve`               | 可以对同一个 `prepare` 的结果多次运行；每次运行都有新的 scope、任务和任期                            |
| 子树                  | 子插件的依赖由父实例的 `inject` 覆盖，贡献由 `provides` 覆盖；带状态的子插件必须在 `children` 中声明 |
| `overlap: true`       | 声明服务段可以与旧的服务尝试并行运行                                                                 |
| 删除 `Update`         | 配置变化一律产生新的一代                                                                             |
| `Plugin.term`         | fencing token                                                                                        |

## 7. 执行能力与执行票据

### 7.1 能力

每个执行**恰好持有一种**能力：

| 能力   | 获得方式                                                   | 入场关闭时                               |
| ------ | ---------------------------------------------------------- | ---------------------------------------- |
| 根操作 | 入口适配器 `Graft.operation`；没有能力的外部回调会自动获得 | 在入场队列中等待                         |
| 借用   | `Graft.borrow(operation, effect)`                          | 不等待                                   |
| 阶段   | 转换授予准备、服务、派生、迁移、清理这些阶段               | 不等待；绕过业务入场，但计入阶段的清理   |
| 控制   | 控制面入口                                                 | 不等待；执行业务调用时必须先以根操作入场 |

| 情形                              | 规则                                                                                                                                                       |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 操作 scope                        | 票据一直持有到操作 scope 的清理全部结束                                                                                                                    |
| `forkChild`                       | 继承能力                                                                                                                                                   |
| `forkScoped`                      | 只有挂在操作 scope 上时才继承；否则必须显式借用                                                                                                            |
| `forkDaemon`、捕获 runtime 的回调 | 能力失效后**失败即关闭**                                                                                                                                   |
| `Plugin.fork` 任务                | 不继承；每个工作单元自己入场，协助已有操作时显式借用                                                                                                       |
| 流                                | 票据持有到流结束、取消或终结                                                                                                                               |
| 提供方上下文                      | 处理器以提供方的服务运行，只转发允许列表中的元数据（能力、`Origins`、追踪）。Effect RPC 的上下文合并（`RpcServer.ts:590`）不会自动保证这一点，需要显式实现 |
| 清理期间的取消                    | 取消请求发出后，能力仍可用于清理期间的嵌套调用；后代借用照常登记                                                                                           |

### 7.2 票据账本

**每次跨单元调用都对应一张票据**，由内核的账本持有，与发送单元的生死无关：

| 规则           | 内容                                                                                                                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 所有者         | 每张票据属于一个已入场的操作，或一个转换阶段                                                                                                                                                              |
| 派发前登记     | 后代票据在派发前登记，父子关系记入账本                                                                                                                                                                    |
| 结果与完成分开 | `Result` 只表示调用方可以继续；`Completed` 表示接收方的执行连同终结器都已结束。只有在清理确实完成后，`Completed` 才能附在 `Result` 上一起发回。终结器在成功响应之后才失败的，作为清理失败报告给票据所有者 |
| 信用           | 执行信用一直持有到 `Completed`，而不是 `Result`，这样快速返回、慢速清理的调用不会无限堆积                                                                                                                 |
| 进度保留       | 为取消、完成确认和控制流量预留容量。后代调用不会无限等待祖先手里的许可；超出就显式拒绝                                                                                                                    |
| 单元死亡       | 只结算该单元里的票据。它派发出去的后代票据，需要各自的完成确认或终止证据                                                                                                                                  |
| 断连           | 没有终止证据就保留票据。终止证据只有三种：完成确认、Worker 已终止、进程已退出。fencing 不算                                                                                                               |

开销是每次调用固定多出几条消息，账本的存储量与未完成的执行数量成正比。

## 8. 转换协议

### 8.1 计划

1. **Describe**：候选单元加载定义，返回声明。
2. **求差**：变化闭包包括以下实例：
   - 定义、模块闭包或配置变化的实例；
   - 新增或删除的实例；
   - 所需操作不再有提供方的消费者；
   - 分组变化所牵涉的整组。

   以上在新旧两种分组上计算到不动点，并纳入 realm 解析、可选依赖与回退、结构子树。

3. **校验**：契约操作集合、线上表示的可用性、来源冲突、状态迁移路径、启动图中的环、外部步骤与 PONR、预计窗口、容量。

### 8.2 执行

**Prepare**：候选单元代在旧单元继续服务时完成所有可以提前的准备。失败只终止候选单元。

**静默切换**：

1. 关闭根入场。
2. 等待执行静默，包括后代票据。

   ——以上两步不是破坏性的——

3. 按退役图的逆序停止旧的服务尝试，让写入者完成清理。
4. **冻结并导出状态**：每个实例在自己的单元内编码状态，内核把收到的编码检查点作为不透明数据保存，并回送确认。
5. 收到检查点确认后，按退役图终止不在保留之列的旧单元代。
6. 在候选单元内迁移状态（编解码和迁移都在单元内完成，内核不执行它们）。
7. 按启动图执行剩余的准备节点和服务节点；先安装暂存路由，再派生、确认。
8. 提交快照，重新打开根入场。

**重叠切换**：闭包内全部成员都标记了 `overlap`
时，新旧服务尝试并行运行；提交后，旧单元满足执行静默即可退役（无状态，不需要导出）。

### 8.3 等待与结局

| 阶段                                  | 到期                                                                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 准备                                  | 中止，终止候选单元                                                                                                                                     |
| 执行静默                              | 按策略选择：中止（入场重新打开，状态不变），或中断剩余执行后继续                                                                                       |
| 停止旧服务尝试                        | 先尝试导出状态；导出不成，再终止单元，并报告状态丢失                                                                                                   |
| 迁移与新服务                          | 恢复：先取得候选的清理证据（单元已终止，且它派发出去的后代票据都已结算），再在旧侧开始新的服务尝试，恢复导出的原始检查点；如果旧单元已经退役，重新准备 |
| 原生代码卡住、runner 断连且租约未到期 | `Stuck`，并附上证据                                                                                                                                    |

试运行期间回滚时，先**导出候选当前的状态**，再终止候选单元。导出前被强制终止的，结局为
`RecoveryFailed`，并标明状态丢失。

### 8.4 PONR、试运行、结果

- PONR 在派发第一个不可逆动作之前写入日志。
- 试运行的健康判定：闭包内的实例全部
  `Active`；每个服务尝试的契约失败率与延迟在阈值内；`Plugin.probe` 通过。
- 结果分为：`Accepted`、`Aborted`、`Recovered`、`RolledBack`、`RecoveryFailed`、`Stuck`、`ForwardOnly`，均附带完整的 cause 和所处阶段。
- 转换期间暂停
  `retry`。服务尝试重启时，scope、任务和任期一律换新。恢复 fiber 由协调器持有。

### 8.5 保留资格

满足以下全部条件的旧代才被保留：

- 它的准备期依赖都不在闭包中，并且在整个保留期内保持有效；
- 它所在的单元代中，没有成员需要按退役图终止这个单元；
- 保留所需的容量已经预留（第 12 节）。

保留中的代一旦失效，立即关闭，并保留完整的 cause。

## 9. 交接状态、外部步骤与控制协议

### 9.1 交接状态

```ts
export const Ledger = Plugin.state("@acme/checkout/Ledger", {
	current: 2,
	versions: { 1: LedgerV1, 2: LedgerV2 }, // checkpoints use the portable wire representation
	initial: () => LedgerV2.make({ orders: [], totals: Totals.zero }),
	migrations: [Plugin.migrate(1, 2, { up, down })], // pure: Result, no services
})
```

- 身份由实例身份加状态名组成。检查点使用可移植的线上表示，在单元内编码，内核只把它作为不透明数据保存。
- 迁移是纯函数，在冻结值上执行；迁移路径取最短路径，存在歧义就报错。
- expand / contract：expand 阶段，试运行期写入的数据必须能被 `down`
  无损表达；contract 只能在上一次 expand 被接受之后进行，且不可回滚。
- 切换前做一次往返检查，只作防护用。`down` 失败时结局为
  `RecoveryFailed`，不会悄悄丢掉试运行期的写入。

### 9.2 外部步骤

`Release.step(name, { precondition, apply, completed, gate })`。派发之前先写入 PONR；`apply`
必须幂等。恢复时只能继续向前推进。

### 9.3 部署控制协议

部署控制协议在引导通道上运行。每条命令都带幂等 id、单元代号和权限纪元，内核先写日志再发出命令。

| 命令                                     | 应答                                      |
| ---------------------------------------- | ----------------------------------------- |
| `Describe`                               | 声明                                      |
| `Prepare`                                | `Prepared` / `Failed(cause)`              |
| `Install(snapshot)` / `Derive(snapshot)` | `Installed` / `Derived(result)`           |
| `Serve(term, checkpoint?)`               | `Ready` / `Failed(cause)`                 |
| `StopServing`                            | `Stopped` / `Timeout`                     |
| `Export`                                 | 编码后的检查点，内核保存后回送确认        |
| `Retire`                                 | 单元终止                                  |
| `Adopt(epoch)`                           | runner 把控制权转交给新内核（第 10.2 节） |
| `Status`                                 | 当前阶段，用于调和                        |

Remote 现有的 runner、传输、认证、租约和 fencing 机制都保留。需要补上的是：准备态候选、这套命令，以及
`Adopt`。今天的 runner 替换是先停后开（`Supervisor.ts:727`），执行通道只允许一个附着（`Execution.ts:219`），这两处都需要改。

## 10. 入口与内核交接

### 10.1 入口插件

入口插件在自己的单元中实现入场协议：打开和关闭入场、维护有界的入场队列、为每个请求获取根操作。

- **入口插件自身升级：** 新入口单元以 `reusePort`
  绑定同一个端口，与旧单元并行。旧单元停止接受新连接，已有连接按 keep-alive、HTTP/2
  GOAWAY、WebSocket 寿命策略排空。平台不支持 `reusePort`
  时，入口会有一个短暂的先停后启窗口。
- **消息消费者：** 入场关闭期间不再拉取新消息。

### 10.2 内核交接

升级 Node、Effect、Graft 或内核本身时：

1. 新进程启动，准备所有候选单元。新进程的入口可以接受连接并放入有界队列，但在提交之前**不入场业务操作**。
2. 协调器权限经日志转移：旧纪元停止分配任期和授权入场，新纪元生效。同一时刻只有一个纪元有效。
3. 状态按第 8.2 节导出、迁移。
4. 旧进程的入口单元进入**中继**模式：已有连接和队列中的请求经本地 socket 转发给新内核的入口，直到这些连接关闭。前一次中继结束之前，不允许开始下一次内核交接，所以不会形成中继链。
5. runner 上的实例通过 `Adopt`
   转交控制权，不替换服务尝试。转交前先调和未完成的借用、路由状态和租约续期。
6. 旧进程在中继义务结束后退出。

`reusePort` 只解决「新连接由谁接受」，交接协议本身是上面这几步。

## 11. 发布层：`@graftland/plugin-release`

发布层本身也是一个普通插件，运行在自己的单元里，只使用公开 API。它属于控制面：在自己仍持有阶段确认或清理依赖期间，不能被停止。

| 构件       | 说明                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------- |
| 不可变发布 | 内容寻址目录；新单元从新目录导入；`node_modules` 随发布一起升级                          |
| 清单       | 依赖闭包、运行时版本、各实例的定义与模块闭包、操作身份与来源、状态版本、部署组、外部步骤 |
| 期望部署图 | 由清单、已解析的配置、现有拓扑编译而来；Loader 提供公开的规划接口                        |
| 日志       | 转换意图、权限纪元、任期高水位、PONR、外部步骤、控制命令、检查点确认、永久发布           |
| 接口       | `build` / `plan` / `apply` / `observe` / `accept` / `rollback` / `abort` / `history`     |

## 12. 容量

| 维度     | 约束                                                                                       |
| -------- | ------------------------------------------------------------------------------------------ |
| 入场队列 | 请求数与字节数上限、等待上限、过载响应、突发包络                                           |
| 调用     | 每单元的并发上限、消息大小上限、聚合字节信用、扇出上限；取消、完成确认、控制流量有预留容量 |
| 流       | 背压，加上每个流的字节上限；块级确认不等于清理确认                                         |
| 单元     | 存活单元、候选单元、试运行中的旧代、长寿命快照的数量与内存预算，在计划阶段预留             |
| 外部资源 | 计划显示切换窗口内的峰值连接数，例如每个单元各开一个连接池，重叠期间翻倍                   |

## 14. 开发模式

`graft start --watch`
是一个开发发布源，变化经协调器转换生效，策略为：不设试运行期，切换即接受，失败即恢复。每次重载都会启动新单元、终止旧单元，因此 ESM 缓存增长和 CommonJS
/ 原生模块的重启限制都不复存在。

## 15. 不做的事

| 不做                       | 原因                              |
| -------------------------- | --------------------------------- |
| 跨单元共享内存或对象       | 需要共享时使用部署组              |
| 依赖放置位置的线上表示     | 只用一种可移植的表示              |
| 隐藏网络失败               | `ContractFailure` 写在类型里      |
| 推导 Schema 兼容性         | 不可变的操作身份 + 精确的集合包含 |
| 远程中间件作为默认         | 中间件留在单元内                  |
| 在内核中运行插件或契约代码 | 内核只负责协调、授权和计账        |
| 原地修改配置（`Update`）   | 与不可变快照矛盾                  |
| 迁移闭包、栈、fiber        | 只迁移 Schema 数据                |
| 并发转换、分布式共识       | 单一协调器加权限纪元              |
| 生产环境监听文件           | 只接受不可变发布                  |

## 17. 上游需求（Effect）

| 需求                           | 原因                                                                          |
| ------------------------------ | ----------------------------------------------------------------------------- |
| RPC 结构化的编解码失败报告     | 今天这类失败直接 `orDie` 或被格式化为缺陷，无法还原出带阶段的 `Protocol` 失败 |
| RPC 完整的逻辑请求生命周期钩子 | 延迟回复在请求生命周期之外运行，完成确认无法界定                              |

在上游支持之前，对应的能力标记为未实现，不在 Graft 中自行绕过。

## 18. 待决问题

| 问题                      | 说明 / 倾向                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **可移植线上表示（3.3）** | 这一条与已撤销的方向相邻，但不相同：契约仍是可执行的 Effect 值，约束的只是传输能运载什么。需要你确认这条边界 |
| 单元的内存与冷启动        | 需要基准测试：每个单元的常驻内存、冷启动时间，以及候选与旧代重叠期间的峰值                                   |
| 调用延迟                  | 直连通道每次往返两跳；需要基准测试，测量时包含编解码和完成确认                                               |
| 部署组的默认推导          | 运维未声明时，按本地边推导出默认组；是否应当强制显式声明？倾向：默认推导，组过大时警告                       |
| 通知的投递保证            | 至多一次还是至少一次；倾向：至多一次加上显式的结果，至少一次交给应用自己的持久化                             |
