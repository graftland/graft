# Graft 的价值定义与价值导向的设计重审

状态：草案 v2，2026-11-07，供讨论。本文不是站点文档，不受
`packages/docs/STYLE.md`
约束。v1 经过一轮独立审查（Codex）后重写，审查结论见附录 A。本文为
[`upgrades.md`](upgrades.md)
的设计提供依据；那份设计将在这里的决定确认后改为 v8。

## 0. 摘要

**定义。**

> **Graft 是面向长期运行的 TypeScript 应用的 Effect 原生插件运行时。**
> 它让扩展的生命周期、依赖和契约显式化，使团队能以**可控的影响范围**更换应用中的任何一项能力：升级、替换、隔离或搬迁，并如实知道每一次变化的结局。
>
> **方向：**
> 发布到生态的插件通过显式契约做到与位置无关；部署位置、权限和升级结局都由运维掌控。

**为什么这样定义。**

- 仓库现在的定位是「Effect 的插件框架」。这只说了实现手段，没说为谁解决什么问题。
- v1 的「为持续变化的软件」又太宽：几乎所有软件都在持续变化，这样的定义无法指导取舍。
- 新定义保留「插件」这个类别：可扩展性本身就是用户问题的一部分，而不只是实现细节。
- 新定义加上了对象，即**长期运行**的应用；加上了承诺，即**可控的影响范围**与**如实的结局**。

更大的愿景，即「让任何软件都能安全地持续变化」，是方向，不是今天的承诺。

**首发人群（滩头）。**

- **人群**：运行常驻机器人或集成网关的小团队。他们的扩展由不同的人独立维护，上游会话重建成本很高。
- **首个对外切片**：网关保持运行，安全地替换其中一个由他人编写的集成插件（第 5 节）。

**需要你决定的事（第 8 节）**：定义与首发人群；默认的分组策略（由实验决定）；接受
`upgrades.md` 3.3 的可移植线上表示。

## 1. 行业痛点

### 1.1 证据如何读

- (P) 表示已在发布方页面核实；(S) 表示只见于二手报道；(旧) 表示 2024 年以前的资料；(未核) 表示审查时未能再次核实。
- 多数调查出自厂商，样本与方法各不相同。它们能说明**痛点存在**，不能说明 Graft
  **能解决**它。
- 每个痛点都按同一个结构呈现：观察到的问题 → 受影响者 →
  Graft 可能改善的机制 → 前提 → 残余问题 → 如何验证。

| 隐性痛点                                                           | 证据状态                                                                                                                                                   | 与 Graft 的关系                                          |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 配置是没有发布管线的代码                                           | 有证据（见 1.2）                                                                                                                                           | 直接相关                                                 |

| 把在进程内设置权限误当作隔离                                       | 有证据：Node 文档 (P)。Worker 能否继承权限状态取决于版本和用法，不能一概而论                                                                               | 直接相关                                                 |

| 运维诊断失败转换的成本、多版本契约的维护成本、租户插件压垮共享后端 | 推断（审查补充）                                                                                                                                           | 这些成本可能抵消吸引力，必须纳入排序                     |
| 开发时热重载不可靠                                                 | 无可信数据                                                                                                                                                 | 不作为行业痛点，只作为 Graft 自身的体验问题              |

### 1.4 相邻系统没有覆盖的组合

调研的范围有限，所以下面写的是「我们**没有找到**这样的组合」，不是「它不存在」。

- Graft 的 Remote 已经能用 Effect
  RPC 契约覆盖三种放置。我们没有找到的是：同时提供**生命周期与演进保证**（版本化的契约、有界的替换、如实的结局、受控的状态交接）的 TypeScript 方案。
- JS 生态中，第三方扩展普遍共享同一个进程或 realm，例如 VS
  Code、Koishi、Backstage、Module Federation。Grafana 只隔离后端插件。
- 带类型的状态迁移加在线替换只存在于 BEAM 中，而且很少被使用：relup 难以测试，大多数 Erlang 团队选择滚动重启。

### 2.2 受益者与排序

排序依据：可触达的团队、实际受到的干扰、替代方案是否够用、采用成本、我们的把握、交付成本。下载量不等于团队数，人群之间也有大量重叠，所以不做精确计算，但要写明取舍。

| 人群                                                                  | 痛点有多尖锐                     | 替代方案是否够用                                        | 采用成本                                         | 判断                   |
| --------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------- | ------------------------------------------------ | ---------------------- |
| **常驻机器人 / 集成网关的小团队**：扩展由他人维护，上游会话重建成本高 | 高：重启会断开会话，插件常常出错 | 不够用：Koishi 安装插件后仍然会重启；OTP 不在 TS 生态里 | 中：Koishi / cordis 用户的概念相近，已有迁移技能 | **首发**               |
| MCP 工具与智能体网关开发者                                            | 中到高：工具变化、凭据、会话     | 部分够用：容器网关、平台自带的续连                      | 中                                               | 相邻人群，第二批       |
| 需要可扩展性的产品与 SaaS 团队                                        | 高：不敢开放扩展                 | 不够用：只能自造插件系统                                | 高：需要完整的安全机制                           | 安全机制端到端可用之后 |
| 一般 TS / Node 后端团队                                               | 低到中                           | 够用：滚动部署 + 持久化状态                             | 高                                               | 不作为早期目标         |
| 插件作者与维护者                                                      | 中                               | —                                                       | 低                                               | 随生态基础设施受益     |
| Effect 社区                                                           | 中：缺少应用层                   | —                                                       | 低                                               | 自然的早期用户         |

把首发人群定得窄，不违背「越多人受益越好」：最终受益的人数取决于能否先在一个人群中建立可复用的价值，然后扩展出去。

### 2.3 与谁集成，而不是重造

| 领域               | 做法                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| 机群编排与渐进发布 | 与 Kubernetes、systemd，以及现有部署工具的分批发布、晋级门槛、中止权限集成；Graft 只负责单个应用内部的转换            |
| 持久化执行         | `effect/workflow`、Temporal、Restate                                                                                  |
| 安全边界           | 进程、容器，以后是 Wasm 组件                                                                                          |
| 契约投影           | OpenAPI（HttpApi）、OpenRPC（Effect 4.1.3 起）、JSON Schema 2020-12（MCP 默认的方言）；只投影定义好的子集，并写明注解 |
| 第三方 MCP 服务器  | 通过容器网关接入                                                                                                      |
| 可观测性           | OpenTelemetry                                                                                                         |

### 2.4 不是什么

- 不是编排器、服务网格、持久化执行引擎，也不是安全沙箱本身。
- 不对任何插件、任何变化承诺「零停机」或「零重写」。承诺是有范围的转换加如实的结局。

## 3. 价值导向原则

| 原则                   | 含义                                                                 | 检验                                 |
| ---------------------- | -------------------------------------------------------------------- | ------------------------------------ |
| 先找到一个人群，再扩展 | 先在痛点最尖锐、替代方案最差的人群中建立可复用的价值                 | 有重复使用者，而且不需要作者亲自操作 |
| 不整体重写             | 每项能力都能从现有代码逐步采用；剩余的迁移工作要测量，并如实说明     | 记录采用所需的改动与时间             |
| 标准优先               | 输出和对接已有标准                                                   | 每项能力写明对接哪个标准             |
| 承诺如实               | 承诺按「已实现、已设计、依赖上游」区分；保证写明范围与结局           | 宣传只引用已实现的部分               |
| 实验决定争议           | 每个有争议的设计决定，都对应一个能改变它的实验                       | 第 6 节的决策规则                    |
| 上游优先               | Effect 缺少的能力向上游提出并参与实现                                | 上游需求清单                         |
| 一方不享特权           | 一方与第三方使用同一套机制、同一套校验；API 访问相同，不等于权限相同 | 第三方一致性测试                     |

## 4. 对设计的重新思考

对象是 [`upgrades.md`](upgrades.md) v7。

### 4.1 采用路径与默认分组（更正 v1）

**更正。**
v1 说 v7 要求先把所有服务改写为契约。这不对：v7 已经允许使用普通服务，并在未声明时把由本地服务连通的实例推导成一个部署组（`upgrades.md`
第 2 节）。逐步采用的路径在 v7 中已经存在。

**真正的问题**是默认分组策略：

| 策略             | 好处                             | 代价                                         |
| ---------------- | -------------------------------- | -------------------------------------------- |
| 按依赖推导（v7） | 组更小，换代范围更小，故障域更小 | 常驻 Worker 更多，内存开销更大               |
| 整个应用一个组   | 开销最小，最接近今天的行为       | 任何变化都替换整个应用单元，故障域是整个应用 |

两种策略都没有消除采用成本：组合根要移动，环境服务要在每个单元中重建（今天的嵌入方式允许调用方传入环境服务），原生依赖要处理，整组替换的代价也要承担。因此只承诺「不整体重写」，并测量剩余的工作量。**默认策略由第 6 节的实验决定**，不现在拍板。

**生态不变式**（保留你的方向）：已发布插件之间的交互，无论是否放在同一处，都遵循同一套契约语义。具体地说：

- 所有已发布插件，不分一方第三方，都要通过相同的一致性检查：放置无关的编码、取消、失败行为、声明的能力；
- 应用内部或显式打包的组合可以使用私有的普通服务；
- 「可以放在任何地方」的意思是「可以放在满足插件声明需求的任何地方」。契约不会把文件系统、数据库事务或硬件依赖一并带走。

### 4.2 安全：由运维决定的策略，绑定到制品

- **信任由运维策略决定，不由包自己声明。**
  一方和第三方使用同一套机制与校验，被授予的权限可以不同。
- **授权绑定到不可变的制品**，范围包括：制品及其依赖、对外暴露的描述（例如 MCP 工具描述）、能力授予、策略。其中任何一项变化，都要重新批准。
- 写明：谁来批准、什么会让批准失效、调用在哪里被拦截、已经缓存了工具列表的客户端如何处理。`list_changed`
  只是通知。
- **威胁模型**要覆盖：安装与构建脚本、导入与
  `Describe`、资源耗尽、出站网络、凭据代管的范围、撤销。运行时沙箱无法追回在安装阶段就被窃取的凭据。
- Worker 是故障与回收边界，不是安全边界。
- 安全路径必须端到端强制执行才算交付。如果首发人群需要运行有敌意的代码，它就成为首个切片的前提。

### 4.3 配置作为发布物：边界写清楚

- 写明哪些东西被版本化：插件配置、特性开关、生成的配置文件。业务数据不在其中。
- 密钥以引用的方式出现在发布中，不把明文复制进发布历史。
- 紧急撤销有显式策略：回滚不能悄悄恢复已经撤销的权限。
- Graft 只负责单个应用内部的转换。机群层面的分批发布、晋级门槛和中止，与现有部署工具集成，不自造。
- 早期只需要一个有界的发布机制，并与现有部署工具集成即可。在证明确实需要全局协调之前，不构建它。

### 4.4 连续性：分成四件事

| 连续性           | 含义                     | 起点                                                     |
| ---------------- | ------------------------ | -------------------------------------------------------- |
| 传输连续         | 连接不断开               | 持有连接的网关保持运行，只替换下游插件。这是首个切片     |
| 逻辑会话连续     | 连接断开后可以续上       | 每种协议自己定义保留时长、重放、去重、令牌过期和最长延迟 |
| 进行中操作的结局 | 已入场的操作有确定的结局 | v7 的执行票据与结果模型                                  |
| 状态连续         | 内存状态跨代延续         | v7 的交接状态。只有当设计伙伴证明确实需要时才实现        |

- 一个永远活跃的流，会让「在空闲点替换」永远等不到空闲点。所以最长延迟必须声明。
- v7 的根入场是应用级的：一个有状态的组件可能拖住无关的工作。这一点需要按组件细化。
- 自动生成的迁移测试用来**发现 bug**，不能证明可逆。还要加上历史状态夹具和领域不变式。`RecoveryFailed`
  结局保留。

### 4.5 契约投影与生态

- 投影是一个定义好的子集，并且必须有注解：HTTP 方法与状态码、认证、调用者身份、流、MCP 描述、副作用。不支持的部分要给出明确的拒绝诊断。投影只是视图，契约本身仍然是 Effect 值。
- 「不腐烂的生态」改为「**减少被迫迁移，并控制不再维护的扩展所造成的影响**」。为此要写明支持窗口、适配器由谁维护、运行时与协议的兼容性、撤销和退役。
- 生态基础设施分两批：
  - 前一批：最小的插件清单、来源记录、兼容性诊断、第三方一致性测试；
  - 后一批：插件市场和大规模迁移工具。
- 不使用「被困住的插件数为 0」这种不可信的指标。

### 4.6 概念：按角色逐步展开

- 应用作者从五个概念开始：插件、契约、部署组、发布、状态。
- 插件作者和运维还需要了解自己那部分能力附带的义务：重叠运行可能重复副作用、外部系统必须执行 fencing、迁移不可逆的步骤。
- 隐藏的只是票据编号之类的内部记账，不是义务本身。

### 4.7 保留与推迟

**保留**：

- 位置透明与失败显式的区分；
- Effect 原生的契约与资源所有权；
- 一方与第三方平等；
- 不可变的操作身份；
- 来源记录，但不把它当作兼容性证明；
- 配置的发布纪律；
- 对不可逆工作如实报告结局；
- 明确的上游需求清单。

**推迟**，各自凭具体需求单独决定，不作为必然的最后阶段：

- 内核交接：在此之前，Node、Effect、Graft 自身升级时无法保持长会话，这一限制要写明；
- Wasm 组件插件；
- 多语言插件；
- 远程中间件。

## 5. 交付顺序

先走更便宜的路径：一个稳定的网关加上一个可替换的单元。等实验证明需要时，再构建完整的快照、票据和状态迁移机制。v7 的完整协议保留为目标架构；早期切片的保证范围有意收窄，并写明。

| 切片 | 内容                                                                                                                                                                                 | 受益者             | 完成标准                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------ | -------------------------------------------------------------------------------- |
| 1    | **网关不停，替换一个他人编写的集成插件**：不可变的候选、最小的契约版本元数据、有界排空、就绪与探针检查、以终止回收、如实的结局（包括修复回滚报告）。第三方插件从第一天起只用公开 API | 首发人群           | 在设计伙伴的真实网关上，一次正常升级和一次故意出错的升级都在预算内完成，结局如实 |
| 2    | 最小的插件清单、来源记录、兼容性诊断、第三方一致性测试                                                                                                                               | 插件作者、首发人群 | 两个独立的插件作者能按清单发布插件并通过检查                                     |
| 3    | 插件与配置的不可变发布、计划、回滚；与现有部署工具集成                                                                                                                               | 首发人群、MCP 网关 | 一次错误的配置能被拦截或回滚                                                     |
| 4    | 首发人群需要的一种契约投影（例如 MCP 工具）                                                                                                                                          | MCP 开发者         | 一个契约以写明的注解变成 MCP 工具                                                |
| 5    | 安全路径（如果首发人群需要，提前到切片 1）                                                                                                                                           | SaaS 团队、MCP     | 攻击用例全部被拦截                                                               |
| 6    | 逻辑会话续连、状态交接                                                                                                                                                               | 证明确实需要的人群 | 实验结果决定是否进行                                                             |
| —    | 内核交接、Wasm 组件、多语言                                                                                                                                                          | 各自按需决定       | —                                                                                |

`upgrades.md`
的工程顺序要服从这个顺序。v7 中支撑切片 1 所必需的部分（单元、终止回收、结局模型、有界排空）先做；其余部分随后续切片实现。

## 6. 如何不闭门造车：实验与决策规则

**实验**：

- 为期四周，在首发人群中找三个团队，外加至少两个独立的插件作者。
- 动手实现之前，先与每个团队约定：
  - 他们现在回避的、或者只能以中断服务的方式完成的、反复出现的那种变更；
  - 当前的中断时长、恢复耗时和采用成本，作为基线；
  - 一次真实的升级，以及一次故意出错的候选版本或配置；
  - 针对他们工作负载的内存、延迟和中断预算；
  - 判定标准：框架作者不在场时，他们是否会重复使用这套流程。
- 对照组：今天的 Graft、一个直接用 Effect 写的受监督进程、以及团队现有的方案。不预设完整框架一定胜出。

**决策规则**：

| 观察到的结果                 | 决定                                                    |
| ---------------------------- | ------------------------------------------------------- |
| 普通的优雅重启已经够用       | 降低状态迁移的优先级                                    |
| 本地服务边妨碍了有用的拆分   | 修改分组与适配器的设计；同时据此确定默认分组策略（4.1） |
| 没有人重复使用这套流程       | 停止扩展架构，重新审视首发人群                          |
| 首发人群需要运行有敌意的代码 | 安全路径提前到切片 1                                    |

公开的 RFC 和基准测试是补充，不能替代上面这些观察。
