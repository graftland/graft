## 0. 价值、原则与验收

### 0.1 价值

> **Graft 是面向长期运行的 TypeScript 应用的 Effect 原生插件运行时。**
> 它让扩展的生命周期、依赖和契约显式化，使团队能以**可控的影响范围**更换应用中的任何一项能力：升级、替换、隔离或搬迁，并如实知道每一次变化的结局。

首发人群是运行常驻机器人或集成网关的小团队。他们的扩展由他人维护，上游会话重建的代价很高。首个场景是：网关保持运行，替换其中一个由他人编写的集成插件。

### 0.2 两条原则

| 原则       | 含义                                                                                               | 违背的信号                                                 |
| ---------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **Scale**  | 一次变更的开销、中断、协调和影响范围，只随**必要的受影响集合**增长，不随无关的插件、作者和租户增长 | 全应用的锁或屏障；全量扫描；一个插件卡住，所有变更都被封锁 |
| **可理解** | 理解一个插件所需的知识，不随系统规模增长。概念有预算；每一步交付都说明它删掉了什么                 | 只为防止机制 A 破坏机制 B 而存在的概念；同一个词有多个含义 |

插件和热替换解决的是同一个 Scale 问题：插件让 N 项独立变化的能力共处一个应用，热替换让其中一项的变化不打扰其余 N−1 项。

### 0.3 对标

| 对标       | 取什么                                                           | 不取什么                                                    |
| ---------- | ---------------------------------------------------------------- | ----------------------------------------------------------- |
| cordis     | 插件、上下文与服务的组合方式                                     | 另造一套概念：直接用 Effect 的 Context、Layer、Scope、Fiber |
| Erlang/OTP | 隔离的执行单元、有强度上限的监督、在线替换、旧调用在旧代码上完成 | appup/relup 的作者负担：影响集合与顺序由框架从声明中推导    |
| Effect     | 结构化并发、资源所有权、类型化错误、`Rpc`、`Schema`、`Schedule`  | 重新定义 Effect 已有的概念；Effect 的缺口在 Graft 里绕过去  |

关于 OTP 的一个更正：OTP 并不保证「所有旧代码都结束后，新代码才开始」。旧代码与当前代码可以同时存在，完全限定的调用进入新版本；清除仍被使用的旧代码会杀掉相关进程。Graft 对应的保证是**按调用绑定**（5.5）：已入场的调用在它入场时的那一代上完成；新调用在策略允许时进入新的一代。

### 0.4 验收准则

最终设计及每一步交付都按下表判定。

| 编号 | 准则             | 判定方法                                                                                        |
| ---- | ---------------- | ----------------------------------------------------------------------------------------------- |
| C1   | 承诺如实         | 每项保证写明范围、结局、实现状态与证据；依赖上游的能力标为未实现                                |
| C2   | 变化局部化       | A 在试运行或 `Stuck` 时，无关的 B 可以变更；增加无关插件，不增加 A 的扫描、屏障参与者或恢复工作 |
| C3   | 并发一致         | 依赖、配置与路由的变化不会产生未经校验的组合；迟到的确认和旧权威不能覆盖新状态                  |
| C4   | 每次变化都有结局 | 单项、批次、取消等待、崩溃恢复都能按稳定身份追查；成员事实、残留状态和未知事实不被总标签掩盖    |
| C5   | 隔离与终止真实   | 插件代码不在内核中运行；超时、退出证据、整组终止的影响分别可观察                                |
| C6   | 首发价值独立交付 | 不依赖状态迁移、完整票据账本或内核交接，就能验证网关会话保持、第三方插件升级与失败恢复          |
| C7   | 生态与信任一致   | 一方与第三方使用相同的公开机制；恢复不能悄悄恢复已撤销的权限                                    |
| C8   | 故障有人负责     | 监督、重试、依赖失效、变更冲突、停止都有明确的所有者、有限的策略和升级处理                      |
| C9   | 开发复用发布语义 | 文件变化进入同一个变更引擎，校验与失败语义相同；延迟与重启整个进程实测比较                      |
| C10  | 概念负担可控     | 按角色列出必学概念与义务；每一步交付说明删除什么                                                |
| C11  | Effect 原生      | 沿用 Effect 的概念；Effect 的缺口走上游，Graft 不另造语义                                       |

### 0.5 不是什么

- 不是编排器、服务网格、持久化执行引擎，也不是安全沙箱本身。机群发布、持久化工作流、沙箱技术都与现有工具集成（`value.md`
  2.3）。
- 不对任何插件、任何变化承诺「零停机」。承诺是**有范围的变更加如实的结局**。
- `Recovered`
  只说明声明范围内的配置与服务恢复了，不是业务事务：已经发生的外部效果撤销不了。

## 1. 运行结构

### 1.1 内核与执行单元

```
 graft start（进程）
 ├─ 主线程：内核
 │   ├─ 变更协调（准入、冲突集合、日志、权威纪元）
 │   ├─ 路由视图与绑定
 │   ├─ 监督者（每个实例的期望状态与重试状态）
 │   └─ 单元的启动、连接授权与终止
 ├─ Worker：网关插件（持有上游连接）
 ├─ Worker：部署组 billing {连接池 P, 插件 D, 插件 E}
 ├─ 子进程（沙箱）：不受信任的插件 B
 └─ 连接：runner 上的插件 C
```

| 规则                   | 内容                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **内核不运行插件代码** | 所有插件，包括网关、发布插件、一方插件，都运行在执行单元中。内核只运行固定的运行时协议，不导入插件模块，也不执行契约的解码与第三方声明检查 |
| **单元之间不共享内存** | 跨单元的交互一律是经过编码的调用。共享只发生在同一个部署组内部                                                                             |
| **回收靠终止**         | 丢弃一代代码的唯一可靠方式是终止它所在的单元                                                                                               |
| **数据通道直连**       | 内核为实际存在的依赖边建立单元之间的直接通道，并负责授权和计账，不转发业务载荷                                                             |
| **环境服务按单元提供** | `FileSystem`、`HttpClient`、时钟、日志在每个单元内提供；intercept 必须是可序列化的配置，或在单元内加载的代码                               |

| 执行单元 | 隔离                             | 故障范围                         | 何时使用                                     |
| -------- | -------------------------------- | -------------------------------- | -------------------------------------------- |
| Worker   | 独立的 isolate、模块图和事件循环 | 单元；但进程级崩溃会波及整个进程 | 默认                                         |
| 子进程   | 独立进程；可加沙箱               | 单元                             | 原生模块、CommonJS、进程级故障隔离、不受信任 |
| Runner   | 另一台机器或容器                 | 单元；断连不等于退出             | 硬件、数据就近、权限边界                     |

Worker 是故障与回收边界，**不是安全边界**。不受信任的插件必须放进沙箱子进程。

宿主进程里只剩内核。内核代码（Node、Effect、Graft 自身）变化时重启进程；保持长会话的内核交接是条件扩展（第 12 节）。

### 1.2 部署组

| 规则     | 内容                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------ |
| 本地服务 | 普通 Effect 服务，值不经编码原样传递。提供方与使用方必须在同一个部署组                                                   |
| 部署组   | 共享一个执行单元的一组实例。运维可以显式声明；未声明时，计划把由本地服务连通的实例推导成一组，并在计划中显示每条入组的边 |
| 解析顺序 | 先按 realm 解析出具体的提供方实例，再推导本地边。不同 realm 中同一个键不会因此合并                                       |
| 放置     | 一组只有一个放置；成员显式要求的放置冲突时，计划报错                                                                     |
| 双重身份 | 既要本地使用、又要远程访问的资源，导出本地服务与建在其上的契约门面两个接口；远程使用者不入组                             |
| 换代     | 组内任一成员的代码变化，都为整组准备新单元；普通失败只按组内依赖重启相关成员；单元崩溃或被终止时影响整组                 |
| 闭包     | 在新旧两种分组上计算到不动点：拆组时仍住在旧单元的成员一起换代；合组时原来的几组整体进入闭包                             |

部署组是显式的取舍：换代范围更大，故障域共享。为节省内存而把无关插件合组，会牺牲 Scale，所以扩大故障域必须显式，默认合并程度由实验决定（第 14 节）。

### 1.3 进程内模式

`Graft.plugin`
是单元内运行时的 API，也可以直接嵌入任何进程使用（用户决定，2026-11-07）。两种用法的保证范围不同：

| 用法                          | 提供                                          | 不提供                                                  |
| ----------------------------- | --------------------------------------------- | ------------------------------------------------------- |
| 经内核（`graft start`、单元） | 第 5–9 节的全部保证：Change、结局、靠终止回收 | —                                                       |
| 进程内嵌入                    | 组合、依赖感知的生命周期、协作式的成员重启    | Change 与结局、靠终止的回收、隔离；代码变化需要重启进程 |

单元内部运行的就是进程内模式：部署组成员的普通失败重启（1.2）由它完成。

| Realm            | 服务与贡献的可见范围                                           | A P O |
| Deployment group | 共享一个执行单元、共同承担单元终止影响的一组实例               | A P O |
| Unit             | 承载执行的 Worker、子进程，或 runner 上的执行                  | P O   |
| Generation       | 一个实例的一次执行，从启动到终止                               | P O   |
| Placement        | 单元的种类与管理方式（宿主直连或 runner）                      | A O   |

| Release          | 不可变的制品、配置（密钥以引用出现）与部署声明                 | A O   |

| Outcome          | 一次变化的结局与证据                                           | A P O |

| 说法                   | 处理                                                 |
| ---------------------- | ---------------------------------------------------- |
| Fork                   | 实例的操作句柄，API 名字；不是部署身份               |
| Candidate              | Change 的目标数据，不单独成为模型                    |

## 3. 身份与所有权

| 对象       | 身份来源                                                     | 持有                                     |
| ---------- | ------------------------------------------------------------ | ---------------------------------------- |
| Instance   | Loader 条目 id；父实例身份加声明名；代码直接加载时的显式命名 | 期望状态、监督状态、任期高水位、历史     |
| Generation | 实例身份加单调代号                                           | 一个 Scope：任务、发布的服务、租约、贡献 |
| Unit       | 内核分配                                                     | 单元本身；承载一个实例或一个部署组的各代 |
| Change     | 内核在准入时分配，独立于发布 id、实例 id 与代号              | 成员事实、阶段、证据                     |

| 规则               | 内容                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 所有权             | 每个 fiber 都归 Scope、`FiberSet` 或 `FiberMap` 所有；迟到的失败 cause 都有归属                                                                                           |
| 租约按代           | 依赖租约属于某一代，不属于 fork。同一实例重叠的两代共用逻辑服务绑定，但执行端点与租约各自独立；把绑定转交给另一个逻辑所有者，要经过冲突检查并结算原所有权                 |
| 任期               | 每一代启动时得到新的任期，任期高水位在授予之前写入日志。外部系统用 `Plugin.term` 做 fencing                                                                               |
| 执行完成证据       | 证明某次调用及其拥有的清理已经结束，只结算这一次执行。客户端收到结果或停止等待，都不等于远端执行完成                                                                      |
| 单元退出证据       | 观察到 Worker 已终止或进程已退出；单元尚未启动时，记录已确认没有创建执行（今天的 `Termination` 的 `Exited` / `NotStarted`）。断连、超时、租约到期、fencing 都不是退出证据 |
| 退出即结算         | 单元退出证据到达时，结算该代持有的运行时租约与反向索引，否则退役与预算会被已退出的持有者阻塞；结算不证明终结器成功，清理事实保留为未知并附 cause                          |
| 正常退役与强制终止 | 正常退役等待相关执行、租约与清理结束。预算耗尽时可以终止整个单元：退出证据只证明执行不再继续，不证明终结器成功，也不证明外部副作用已撤销                                  |
| 单元退役           | 单元中所有成员的执行、租约与义务都结束之后，单元才终止；个别成员的 Scope 可以先关闭                                                                                       |

## 4. 契约

### 4.1 模型

操作和事件是不可变的协议单位，各自有身份
`name@version`。契约是这些单位组成的具名集合。

```ts
export const quote = Contract.operation(
	"@acme/pricing/quote",
	1,
	Rpc.make("quote", { payload: Cart, success: Quote, error: PricingError }),
)
export const Pricing = Contract.bundle("@acme/pricing/Pricing", [quote])
```

| 方面     | 规则                                                                                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 身份     | `name@version` 一经发布不可变，范围包括 Schema、变换、默认值、精炼、错误的含义与编解码依赖                                                                        |
| 演进     | 线上或语义的变化产生这个操作的新版本，其他操作不受影响                                                                                                            |
| 消费方   | 注入契约或其子集。计划在 realm 解析后的同一个服务绑定内，按实际用到的操作身份做精确的集合包含检查，由一个选定的提供方满足；不同键或多个不完整提供方的并集不算满足 |
| 提供方   | `Contract.implement(bundle, handlers)`；可以同时实现同一操作的多个版本                                                                                            |
| 底层     | 就是 Effect 的 `Rpc` 与 `RpcGroup`。Graft 只附加身份与版本元数据                                                                                                  |
| 线上表示 | 只有一种，与放置无关：由 Effect RPC 的序列化选择（JSON 用 `Schema.toCodecJson`）。没有对应编解码器的声明不能用在契约中                                            |
| 来源     | 清单记录每个操作身份来自哪个契约包构建；同一身份出现两个无法解释的定义时拒绝。摘要只核对来源，不证明兼容                                                          |
| 一致性   | 契约包附带请求、响应、错误、流的样例值；一方与第三方插件用同一套检查                                                                                              |

### 4.2 绑定

- 注入得到的客户端是逻辑能力：每次调用时解析到当前路由的那一代；调用一旦派发，就绑定在那一代上直到结束。
- 流在整个生命周期内保持同一个绑定。断开的流不自动续接；续接由领域协议定义游标、重放与去重。
- 删除一个操作版本之前，确认没有未来的绑定需要它，也没有仍钉着它的调用或流。
- 处理器使用提供方的 Context。跨单元只转发明确允许的调用元数据（能力、来源、追踪），不转发任意服务、Scope 或权限。

### 4.3 交互形式

| 形式     | 是什么                     | 跨单元方式                                                                                                                                                                                                                                                                                                       |
| -------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 操作     | 有结果的调用               | 契约操作                                                                                                                                                                                                                                                                                                         |
| 通知     | 事实，带载荷，没有业务结果 | 发出方对每个订阅者调用一个一元投递操作，不使用 Effect RPC 的 notification 请求模式。订阅者处理完成后才确认，入队不算完成。顺序只在同一发出方与同一订阅者的存活投递会话内保证；结果未知时不自动重发，也不越过尚未结算的前一次投递。投递队列有界。语义为至多一次加显式的投递结果；跨重启的重放与去重由领域协议负责 |
| 查询扇出 | 需要聚合结果的分发         | 契约操作，聚合方式写明                                                                                                                                                                                                                                                                                           |
| 中间件   | 环绕下游执行               | 只在单元内，用普通的 Effect 组合                                                                                                                                                                                                                                                                                 |
| 注册表   | 贡献的数据加端点           | 所有者单元负责解释（HTTP 路由、CLI 命令、MCP 工具）；贡献只携带可编码的描述与端点引用                                                                                                                                                                                                                            |

### 4.4 失败与支持范围

| 项                | 内容                                                                                                                  | 状态                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 业务错误          | 保持各自的类型；中断与缺陷仍是 Effect 的 `Cause`                                                                      | 已实现                                                                                                    |
| `ContractFailure` | 系统失败带原因、阶段（入场、请求、执行、响应）与执行结果（`NotAdmitted` / `Unknown`）。只有执行结果能判断重试是否安全 | 依赖上游：Effect RPC 今天对载荷编码与响应解码使用 `orDie`，无法还原结构化的协议失败；不解析错误字符串绕过 |
| 一元调用          | 首批支持                                                                                                              | 普通 Remote 与变更路径都已支持                                                                            |
| 服务端流          | 普通 Remote 已支持；变更路径是否首批支持，由设计伙伴的调用拓扑决定（第 14 节）                                        | 变更路径未实现                                                                                            |
| 延迟回复、discard | 需要 Effect 提供完整的逻辑请求生命周期钩子                                                                            | 依赖上游                                                                                                  |
| 嵌套跨单元调用    | 调用链继承一致的绑定，后代的清理可以结算（完整票据账本，第 12 节）                                                    | 条件扩展；具备之前不宣称整条调用链的保证                                                                  |

## 5. 变更模型

**一切运行态变化都是一个 Change，经同一个协议执行。** 没有第二条变更路径。

### 5.1 今天的路径如何归入

| 今天的路径                     | 归入                                                          |
| ------------------------------ | ------------------------------------------------------------- |
| `Graft.transition`             | 成为执行 Change 的协议本身                                    |
| `plugin-release` 的应用与回滚  | 一个批次 Change，成员是发布中变化的实例                       |
| `Fork.update` / `Fork.restart` | 以实例为目标的 Change；配置变化一律产生新的一代               |
| `Graft.replace` 与全局别名     | 删除：部署身份是实例，不是插件对象；按实例或 realm 选择目标   |
| HMR                            | 开发配置的来源（8.3）                                         |
| Loader 命令编辑、外部刷新      | 以 Loader 条目为目标的 Change；命令编辑带存储版本做比较并交换 |
| Loader 运行态重试              | 归监督者（第 7 节）                                           |
| Remote 模块模式                | 就是放置；与其他插件走同一路径                                |

### 5.2 Change 的组成

| 部分     | 内容                                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 身份     | 内核分配的 Change id                                                                                                                         |
| 来源     | 发布、开发配置、运维命令、Loader、监督者                                                                                                     |
| 目标     | 实例或 realm 选择器，加目标发布或补丁                                                                                                        |
| 前提     | 期望的对象版本（实例、绑定、部署组）；不满足时拒绝，不覆盖                                                                                   |
| 预算     | 各阶段最多等多久：总预算、启动、探针、排空、停止、终止                                                                                       |
| 要求     | 运行哪些探针、试运行至少观察多久。试运行时长是最低观察要求，单独配置，但耗时计入总预算；准入时检查总预算能否容纳试运行与必要的清理、恢复预留 |
| 完成条件 | `Serving`（默认）或 `Committed`，见下表                                                                                                      |

| 完成条件    | 含义                                                                                                                                                                               |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Serving`   | 新增与保留的目标成员已就绪，并通过要求的探针与试运行；删除的成员已停止；本次要求退出的单元已取得退出证据                                                                           |
| `Committed` | 只提交并记录期望状态，不承诺它已经运行成功。之后的运行态协调由监督者发起独立的 Change，关联本次的 Change id，各有自己的结局。非法配置或未通过静态校验的目标不能以 `Committed` 接受 |

### 5.3 成员

计划为每个成员写明**入选原因**、停机范围、策略、恢复目标与容量需求。

| 入选原因       | 例                                               |
| -------------- | ------------------------------------------------ |
| 显式目标       | 定义、模块闭包或配置变化的实例；新增或删除的实例 |
| 同组           | 与变化的实例在同一个部署组（新旧分组上求不动点） |
| 本地依赖       | 通过本地服务捕获了变化实例的值的使用方           |
| 契约失去提供方 | 所需的操作身份不再有提供方的消费者               |
| 结构子树       | 父实例换代时，在它的 Scope 中创建的子实例        |

**通过仍然兼容的契约使用变化实例的消费者，不入选。**
稳定的路由切断了不必要的重启传播。这一条是 Scale 的关键。

成员在准入时确定。首版要求计划覆盖新增子实例的声明及其共享资源需求，集合内的子实例登记不算扩大范围。执行中发现集合外的冲突对象时，不等待持有它的 Change，也不直接执行：清理本次暂存，重新规划、重新准入。

### 5.4 策略

| 策略      | 何时用                                             | 过程                                                           |
| --------- | -------------------------------------------------- | -------------------------------------------------------------- |
| `Overlap` | 插件声明 `overlap: true`，经契约提供服务，放置支持 | 新代与旧代并行；新代就绪并通过探针后切换路由；旧代排空后退役   |
| `Restart` | 其余情况；或调用方显式要求                         | 暂停受影响能力的新入场；旧代排空、停止；新代启动；重新打开入场 |

- 没有就地更新（`InPlace` /
  `Update`）。配置变化产生新的一代：恢复与观察只有一种形态。
- `Overlap`
  可能重复执行定时任务或争用独占资源，所以必须由插件声明，不由框架推断。
- 以部署组为单位换单元时，随之重启的所有成员及其资源组合都必须允许重叠；一个成员声明
  `overlap` 不足以让整组重叠。
- 停止与启动按依赖排序：消费者释放之前不关闭提供方的资源；启动图做环检测。
- runner 首版只支持 `Restart`：今天 runner 打开同身份执行时会先停止旧执行。
- `Handoff`（带状态交接）是条件扩展（第 12 节）。

### 5.5 执行与「旧的先完成」

```
Overlap：校验、准备候选 → 启动、就绪、探针 → 提交路由，开始试运行
       → 排空、停止并回收旧代 → 确认完成条件与清理义务 → 记录结局
Restart：校验、可提前的准备 → 暂停受影响能力的入场 → 排空、停止旧代，确认资源可以安全复用
       → 启动候选、就绪、探针 → 提交路由，恢复入场 → 试运行、完成必要的清理 → 记录结局
```

任一阶段失败，都先结算本次创建的执行，再看旧代是否仍可用，决定中止还是恢复。

| 保证           | 精确含义                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 按调用绑定     | 已入场的调用在它入场时的那一代上完成，不会被偷偷换代                                                                                                     |
| 旧代先排空     | 旧代在它的调用全部完成后才停止；排空预算到期时，按要求中止或中断剩余调用，结局写明被中断的调用                                                           |
| 入场不拒绝     | `Restart` 的切换窗口内到达的请求在有界队列中等待；超出容量或等待上限时给出声明的过载响应                                                                 |
| 失败只影响候选 | 只在旧代尚未停止、依赖仍然有效且仍然健康时成立。旧代已经停止或失效时（例如 `Restart` 中候选启动失败），必须重新执行恢复目标，恢复也可能失败              |
| 排空覆盖远端   | 排空计数覆盖支持范围内的远端执行及其清理（执行完成证据）。完整的后代票据账本可以后置，单跳的完成与取消证据不能后置；上游无法提供证据的调用形态明确不支持 |
| 退出有证据     | 本次需要退役的单元在取得退出证据后才算退役，然后才能 `Accepted`；取不到时结局为 `Stuck`。组内普通失败只重启成员时，代结束不要求单元退出                  |

暂停的只是受影响能力的新入场，不是整个应用的入场。

### 5.6 期限与终止

期限只约束协调器等多久，不保证执行已经停止。

| 放置           | 超时后                                                                   |
| -------------- | ------------------------------------------------------------------------ |
| Worker、子进程 | 终止单元，等待退出证据。Worker 的终止是「尽快」，不是固定上限            |
| Runner         | 断连且租约未到期时，没有退出证据，结局为 `Stuck`                         |
| 部署组中的成员 | 单个成员清理卡住时，预算耗尽后终止整个单元；计划与结局列出同组的连带影响 |

同步阻塞事件循环的代码，连 `Stuck`
也无法在它自己的单元里按时报告；内核在单元外判定。

### 5.7 结局

| 结局             | 含义                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| `Accepted`       | 完成条件与本次必须完成的清理义务都已满足                                 |
| `Aborted`        | 没有达成目标，也不需要重建旧代；旧代保持可用                             |
| `Recovered`      | 没有达成目标，已重新执行恢复目标并满足其完成条件；不以是否已切换路由为界 |
| `RecoveryFailed` | 恢复没有达到目标                                                         |
| `Stuck`          | 无法取得退出证据，相关对象被保留，等待运维处理                           |

每个结局都带完整的 cause（或其诊断引用，见 9.2）与所处阶段。

**批次结局**不只是一个总标签。每个计划成员都有：

| 字段     | 内容                                   |
| -------- | -------------------------------------- |
| 起点     | 变更前的版本与健康状态                 |
| 目标     | 期望的版本                             |
| 执行     | `NotStarted`，或执行到的阶段与结局     |
| 补偿     | 是否补偿，补偿的结局                   |
| 现状     | 实际运行的版本、健康状态、是否符合期望 |
| 可恢复性 | 能否再次恢复；为什么不能               |

批次中互不相关的成员可以并行执行。跨成员默认**不**承诺原子可见或原子补偿。批次失败时：停止派发尚未开始的成员；结算在途的成员，迟到的成功也纳入结果与补偿集合；按依赖关系的逆序补偿，无依赖的成员独立处理。相关的冲突对象保留到批次结算，不在单个成员
`Accepted` 时提前释放。`plugin-release` 今天的串行逆序补偿是这一规则的特例。

### 5.8 恢复

- 恢复目标是旧的期望配置。输入**重新解析**（例如轮换后的凭据），并重新通过**当前**的信任检查：撤销的权限不会被恢复。
- 依赖租约与绑定总是重新获取。
- 只有声明了状态交接保证的 Change，才要求恢复试运行后的内存状态（第 12 节）。没有声明时，`Recovered`
  只表示配置与服务恢复，不表示业务状态或外部副作用已撤销。

### 5.9 所有权、取消与观察

| 动作 | 语义                                                                   |
| ---- | ---------------------------------------------------------------------- |
| 提交 | Change 被准入后由运行时拥有，得到稳定的 id                             |
| 等待 | 调用方等待结局；取消等待不取消 Change                                  |
| 取消 | 显式操作；在旧代被改变（停止或切走路由）之前有效，之后按恢复处理       |
| 关闭 | 运行时关闭时先关闭准入，再取消已准入的 Change；结局保留被中断的阶段    |
| 观察 | 按 id 查询或订阅成员事实、阶段、剩余预算、仍持有租约或未确认退出的对象 |

## 6. 并发

**一个控制权威，多个互不冲突的 Change 并行。** 全应用的 `Busy`/`Stuck`（今天的
`transition.ts:1055-1056`）与「一次只执行一个转换，包括试运行期」的规则删除。

### 6.1 协议

1. **计算读写集合。**
   包括目标实例、新旧部署组、被修改的服务绑定、依赖解析条件（可选依赖的缺席也是一个读取条件）、相关的注册表贡献、授权版本。
2. **原子准入。**
   在一个 STM 事务中检查集合是否与在途的 Change 冲突，并登记整个集合。冲突时拒绝（`Busy`，附冲突对象），不排队，不接管。首版一次登记完整集合，不做逐步加锁。
3. **只暂存，不覆盖。**
   准备阶段只产生暂存的路由视图（安装不等于激活）。确认绑定到 Change
   id、单元代与视图版本；迟到的确认不计入。激活前，受本次补丁影响的必要参与方都要完成暂存视图的安装与派生确认。候选启动所需的路由先安装；生命周期与派生不等待本次暂停的业务入场，也不等待自己的发布。部分确认失败只清理本次暂存；提交后某个参与方失败，表现为显式的不可用，不自行回退到旧视图。
4. **按补丁提交，检查局部版本。**
   提交的是本 Change 的补丁，不是规划时读到的完整旧状态。A 与 B 从同一个基础出发，只要读写条件兼容，提交后同时包含 A 与 B。
5. **冲突由依赖决定，不由位置决定。**
   A 捕获了 B 的本地资源时，B 的退役与 A 的变化冲突；A 只通过兼容的契约使用 B 时不冲突。
6. **业务入场与变更准入分开。**
   暂停的是受影响能力的新入场；已入场的工作沿用自己的绑定。
7. **`Stuck` 只封锁它的冲突集合**，包括仍持有它租约的消费者。

| 冲突对象 | 两个 Change 何时冲突                 |
| -------- | ------------------------------------ |
| 实例     | 成员集合相交                         |
| 服务槽   | 撤回或发布同一 realm 中的同一个键    |
| 依赖边   | 一方的撤回要等另一方持有的消费者排空 |
| 部署组   | 共用执行单元，新旧两种分组都算       |
| 注册表项 | 贡献同一个注册表中的同一个键         |

### 6.2 纪元、版本、任期、日志

| 机制     | 防什么                                                   |
| -------- | -------------------------------------------------------- |
| 权威纪元 | 旧的控制者。只在控制权威转移时递增，不随每个 Change 递增 |
| 对象版本 | 过期的计划覆盖新的状态                                   |
| 任期     | 旧的一代继续写外部系统                                   |

日志顺序：意图在对应动作之前；提交决定在对外激活之前；事实在确认之后。不同 Change 的记录可以交错，只要求各自的因果顺序与共享对象的提交顺序。日志按追加写入，不在每次持久化时重写全部历史。

STM 事务与互斥临界区只覆盖短的状态变更，不跨远端等待。已准入的 Change 对冲突对象的逻辑保留持续到它结束，试运行与恢复期间仍然有效，但不阻塞无关对象。共享 CPU 与 I/O 的饱和由容量约束（第 10 节），不承诺「任何负载下延迟不变」。

**并发恢复**：A 恢复时只恢复它仍拥有的版本，不覆盖 B。A 的旧配置与 B 已接受的结果不兼容，说明计划或冲突计算有缺陷；但仍要产生如实的结局：停止冲突的推进，按实际恢复能力报告
`RecoveryFailed` 或 `Stuck`，保留诊断，不覆盖 B 的结果。

### 6.3 崩溃恢复与控制面所有权

| 规则            | 内容                                                                                                                                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 恢复检查点      | 按成员记录最近已接受的期望版本及其提交顺序。不同 Change 的成员检查点可以组合；一个未完成的 Change 不会撤销无关的已接受结果                                                                |
| 未完成的 Change | 重启后按原 Change id 调和记录与执行事实：先确认旧执行已退出或保留为 `Stuck`，再从声明的恢复目标启动；不能从「重启了旧版本」推断之前的动作没有发生。每个未完成成员都补记实际状态与未知事实 |
| 请求关联        | 调用方提交稳定的请求键，准入记录把它映射到 Change id。相同的键与内容返回原记录，不重复执行；相同的键、不同的内容则拒绝                                                                    |
| 控制面所有权    | 已准入的 Change 不归发起它的插件的 Scope 所有。承担记录或阶段确认义务的插件（如发布插件），在义务完成或交接之前不能被本次 Change 停止；没有交接能力时拒绝这种自我替换                     |
| 记录失败        | 停止推进，保留可观察的未确定状态                                                                                                                                                          |

## 7. 监督

**监督者拥有期望状态与重试状态；Change 拥有一次动作。** 两者不竞争同一个实例。

- 监督者在实例的长期 Scope 中，用 Effect 的 `Schedule`
  表达重试与退避；同一期望配置与依赖条件下的连续失败共用同一个调度进度。
- 内核只执行固定的监督协议，以及由可编码参数构造的内建
  `Schedule`。插件自定义的可执行策略在内核外运行，通过受限的控制协议提交建议；插件闭包不能成为内核配置（今天的
  `retry` 是插件提供的 `Schedule` 值，需要随之改变）。
- 监督者的一次重启，本身就是一个来源为「监督者」的 Change，经同一准入。
- **重启强度**（对标 OTP）：在一个时间窗口内的重启次数超过上限时，监督者停止重试，把失败升级给部署组或应用的监督者，并保持可观察的失败状态。计数只统计实际发起的故障恢复尝试：`Busy`
  拒绝、计划内换代、等待依赖不消耗次数；计数不因创建新的一代而清零；每一层都有有限的预算。超过上限后默认隔离失败的实例或必要的部署组并通知上层，不自动重启无关实例；更大范围的重启必须由显式策略授权。

| 事件               | 处理                                         |
| ------------------ | -------------------------------------------- |
| 当前一代失败       | 立即撤回失效的路由；按监督策略决定下一次尝试 |
| 候选准备失败       | 结束这次 Change；不对候选无限重试            |
| 试运行失败         | 由这次 Change 恢复；监督者不另起竞争的尝试   |
| 依赖撤回           | 见下文                                       |
| 重试耗尽           | 升级处理；保持可观察的失败                   |
| 单元崩溃           | 先对整组结算，再按组的策略恢复               |
| 清理未取得退出证据 | 不启动争用同一资源的新执行                   |

**依赖撤回**：

- 依赖失效立即关闭旧绑定的新业务入场，不因 `Busy`
  被丢弃。已持有租约的消费者仍可完成必要的清理；提供方资源在消费者释放之前保持有效，除非故障或强制终止已让它不可用（今天激活的停止顺序就是先撤回、再等消费者释放）。
- 当前 Change 计划内的撤回是它自己的执行步骤，不触发自我抢占。
- 非计划的失效使相关计划的前提失效：通知当前所有者停止推进、结算候选与清理；在旧所有者释放之前，不并行启动另一次尝试。重新检查当前依赖与授权后，能满足恢复目标就恢复；不能满足就报告
  `RecoveryFailed`，或在未确认终止时报告
  `Stuck`，由监督者保留期望状态，等待依赖或升级处理。恢复不会重新启用失效的绑定。

## 8. 发布、Loader 与开发配置

### 8.1 发布

`@graftland/plugin-release` 是一个普通插件，运行在自己的单元中，只使用公开 API。

| 构件       | 说明                                                               |
| ---------- | ------------------------------------------------------------------ |
| 不可变制品 | 内容寻址的目录；新单元从新目录导入；未捕获的外部运行依赖如实标出   |
| 配置       | 与制品一起版本化；密钥以引用出现，不复制进发布历史                 |
| 撤销       | 回滚不会恢复已经撤销的权限                                         |
| 日志       | Change 的意图、成员事实、批准；按追加写入，允许多个 Change 交错    |
| 接口       | `build` / `plan` / `apply` / `observe` / `rollback` / `history`    |
| 机群       | 只负责单个应用内部的变更；分批发布、晋级门槛与中止交给现有部署工具 |

### 8.2 Loader

| 来源               | 规则                                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| 外部编辑           | 文件已经落盘，视为新的期望版本；失败时保留磁盘上的意图，报告它与运行态的差异 |
| 命令编辑           | 基于明确的存储版本，比较并交换                                               |
| 运行成功、写入失败 | 结局写明；重启后以存储为准                                                   |

### 8.3 开发配置

**HMR 不再是一条独立的变更路径，而是发布流水线的开发配置。**
开发与生产走同一个变更引擎、同一套校验、同一种结局。

| 阶段     | 发布配置                           | 开发配置                                                           |
| -------- | ---------------------------------- | ------------------------------------------------------------------ |
| 来源     | 发布源文件                         | 监听到的文件变化；一个 Change 执行期间的编辑合并成下一个 Change    |
| 构建候选 | 捕获内容寻址的目录                 | 产生本次执行字节稳定的模块闭包（构建工具的输出即可），不做长期归档 |
| 校验     | 契约、依赖、放置、配置、策略适用性 | 相同                                                               |
| 策略     | 插件的设置                         | 相同：开发中就能暴露「重叠运行不安全」「探针写错」                 |
| 试运行   | 发布的默认值                       | 运行探针；试运行时长默认为零                                       |
| 记录     | 持久日志、信任批准                 | 只在内存中                                                         |

- 不直接引用正在变化的工作目录：准备期间的保存会让同一个候选读到不同版本的文件。
- 开发来源与 Loader 遇到 `Busy`
  时保留最新的未应用输入，等冲突对象变化后重新规划、提交；不丢编辑，不忙轮询。收集输入不等待当前 Change 完成。
- 开发配置不能进入生产：开发候选没有制品身份与批准记录，安装了信任策略的应用拒绝它。需要演练审批流程时使用发布配置。
- **延迟（用户决定，2026-11-07）**：开发时慢一些可以接受，基准是重启整个进程。按单元换代只重启变化的插件，其余插件与会话保持运行。验收时实测「从保存到新代码开始服务」与重启整个进程的对比；预热 Worker 等优化只在确有需要时再做。
- 开发代码替换完成后旧单元被终止，所以 HMR 今天的限制随之消失：ESM 缓存无限增长、CommonJS 与原生依赖需要重启、别名与身份冲突导致的跳过。

## 9. 运维与信任

### 9.1 观察

一次 Change 的观察结果必须回答：

- 谁发起，为什么包含这些成员；
- 现在卡在哪个阶段，剩余预算多少；
- 谁仍持有租约，谁还没有取得退出证据；
- 现在实际运行什么，是否符合期望；
- 哪些恢复已完成，哪些需要人工处理；
- 如何关联完整的 cause、日志与追踪（OpenTelemetry）。

### 9.2 结局与诊断分层

| 层   | 内容                                | 保存                           |
| ---- | ----------------------------------- | ------------------------------ |
| 结局 | Change id、成员事实、阶段、诊断引用 | 发布日志，持久                 |
| 诊断 | 完整的 cause（可能含秘密）          | 受控的诊断存储，有声明的保留期 |

今天持久摘要只记录 `hasCause`，无法定位问题；改为诊断引用。

### 9.3 信任

| 规则           | 内容                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| 由运维决定     | 信任等级由运维策略按实例、包名与制品摘要分配，不由包自己声明；一方与第三方走同一套检查                     |
| 绑定到制品     | 批准绑定到制品身份、对外暴露的描述（如 MCP 工具描述）、能力授予与策略版本；任何一项变化都需重新批准        |
| 先失效，后可见 | 对外描述或授予变化时，先记录并使旧批准不再满足调用准入，再暴露新的视图；客户端缓存的旧列表不能绕过这项检查 |
| 准入时检查     | 在计数调用的同一个事务中检查所选的一代与批准                                                               |
| 撤销           | 先阻断入场；恢复与回滚都重新检查当前策略                                                                   |
| 隔离           | 不受信任的插件必须放进沙箱子进程；启动器不可用时拒绝运行                                                   |
| 威胁模型的边界 | 安装与构建脚本在运行时沙箱之前执行；被明确授予的能力仍可能被滥用；资源耗尽只做有限防护                     |
